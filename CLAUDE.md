# עכבר עו״ש (OshRat)

> If you named the Xcode project something other than `OshRat`, update the name in this file to match it.

## What this app is

A personal finance app, in Hebrew, that helps one person track their money and feel in control of their financial state. There is intentionally **no connection to banks or investment providers** — the user enters and updates all balances and transactions manually. This is both a privacy choice and a simplicity choice.

This is also a **learning project**: the developer is new to iOS development. Prefer clear, idiomatic, well-commented Swift, and briefly explain non-obvious decisions as you go rather than only producing code.

## Names

- Project / module name (code, ASCII): `OshRat`
- Display name (what users see, Hebrew): עכבר עו״ש
- Theme (for a later design phase): rat / mouse themed. No design work yet.

## Platform & stack

- **Two bundle IDs, by build configuration.** **Release** is `com.oshrat.app` — the App Store app, and the copy used for real. **Debug** (every Run from Xcode) is `com.oshrat.app.dev`, named **"עכבר עו״ש פיתוח"** on the home screen with an amber icon (`AppIcon-Dev`, the release icon hue-shifted 150° — the navy and gold rotate, the grey rat stays grey), so both can be installed side by side with separate data. Widgets are `…app.widget` / `…app.dev.widget`, the App Intents extension `…app.intents` / `…app.dev.intents` (an extension's ID must extend its app's). Each variant has its own deep-link scheme — `oshrat` / `oshrat-dev`, from the `APP_URL_SCHEME` build setting, surfaced to code as the `OshRatURLScheme` Info.plist key — because two apps claiming one scheme open unpredictably. The release ID is permanent once a build is uploaded to App Store Connect; don't change it. **Edit per-configuration names in Build Settings, not the General tab**: its Display Name field writes every configuration at once, which is how the release app once shipped as "עכבר עו״ש פיתוח". So does the **iCloud container**: `iCloud.com.oshrat.app.dev` / `iCloud.com.oshrat.app`, from the `CLOUDKIT_CONTAINER` build setting (entitlements use `$(CLOUDKIT_CONTAINER)`; code reads the `OshRatCloudKitContainer` Info.plist key), so the dev build syncs its own data, never the real app's. So does the **App Group**: `group.com.oshrat.app.dev` / `group.com.oshrat.app`, from the `APP_GROUP` build setting on the app and the intents extension (entitlements use `$(APP_GROUP)`; code reads the `OshRatAppGroup` Info.plist key) — it holds the waiting Apple Pay payments both processes share (`PaymentInbox`). Anything else added per-app later (push) needs a dev and a release variant too.

- iOS only. Deployment target: **iOS 26** (project setting is 26.5). Uses SwiftData plus iOS 26 Liquid Glass APIs (e.g. `glassEffect` in `HomeBottomBar`).
- UI: SwiftUI.
- Persistence: SwiftData on the device, **mirrored to the user's own private iCloud database** (CloudKit) when the device is signed in — see *iCloud sync* below. No backend or server of our own, and no other network calls — with **one explicit exception**: see *FX rates* below.
- Architecture: MVVM — SwiftUI views → view models → services → SwiftData models.
- Charts: Swift Charts (Apple's native framework).
- Language & layout: Hebrew, right-to-left. The app is **pinned to Hebrew on every device** (`CFBundleLocalizations = [he]` in `OshRat/Info.plist`, `developmentRegion = he`), so it always renders RTL regardless of the simulator/device system language. User-facing Hebrew is currently written inline as `Text("…")` literals; Swift treats these as `LocalizedStringKey`s and Xcode auto-extracts them into `OshRat/Localizable.xcstrings` (whose `sourceLanguage` is `he`, so the key *is* the final text — nothing to "translate"). Let SwiftUI mirror RTL automatically; for a `+`/`-` sign on an amount, wrap it in U+2066…U+2069 so the bidi-neutral sign stays on the visual left (see the summary cards).
- **Goal — finish the String Catalog migration:** make `Localizable.xcstrings` the source of truth for user-facing text, chiefly to get correct Hebrew **plurals** (1 / 2 / many differ, e.g. `%lld תנועות`) and to disambiguate / positionally reorder interpolated args. Migrating is safe and does **not** change the app's language: keys stay Hebrew and `CFBundleLocalizations = [he]` keeps it Hebrew + RTL. Do **not** add a second language (e.g. `en`) to the catalog or bundle localizations unless the app is genuinely going multilingual — that would let a non-Hebrew device flip the layout to LTR.
- Multi-currency: every account, holding, transaction, budget item, and goal carries its own ISO currency code (e.g. `ILS`, `USD`). The dashboard rolls everything into the user's **preferred currency** via cached FX rates (see below), falling back to per-currency / "FX unavailable" when rates are missing. Conversion goes through `CurrencyConverter`.

## FX rates (network exception)

The app pulls daily reference exchange rates from **Frankfurter.dev** (`https://api.frankfurter.dev/v1/latest`) so the dashboard can roll multi-currency totals into the user's preferred currency. Apart from iCloud sync (which goes to the user's own private iCloud, below), this is the *only* network call the app makes.

Rules of the exception:
- **Public reference data only.** Frankfurter publishes ECB rates. No auth, no API key, no user identifiers in the request.
- **Cached aggressively.** Rates are stored in a `FXRateSnapshot` SwiftData row and refreshed at most once per 24h.
- **Graceful fallback.** If the fetch fails (or the cache is empty), the dashboard falls back to per-currency totals with a small "FX unavailable" note. Nothing in the rest of the app depends on a successful fetch.
- **Don't expand this exception** without updating this section. Anything that sends user data over the network — bank, brokerage, market-data, analytics, telemetry — needs a separate, deliberate decision.

## iCloud sync

The one deliberate decision so far to send user data off the device: the SwiftData store syncs to the user's **own private iCloud database** through CloudKit (`PersistentStore.configuration`: `cloudKitDatabase: .private(<variant's container>)`). Apple holds it, only the user can read it, and no server of ours is involved. **Always on** when the device is signed into iCloud — there's no switch — and fully optional: signed out or offline the store simply works locally and catches up later; nothing in the app waits for iCloud. Settings shows the state ("מסונכרן עם iCloud" / "לא מחובר ל-iCloud — הנתונים נשמרים רק במכשיר", via `CloudAccountService.status()`). What stays on the device on purpose: `UserDefaults` state (waiting Apple Pay payments, the onboarding draft, device preferences).
- **Model rules CloudKit enforces** (the container refuses to load otherwise — it checks at launch): every stored property optional or defaulted; **every relationship optional, to-many included** (`[T]? = []`, read as `x ?? []`); every relationship with an inverse; no unique constraints; changes only additive (see the versioning note in Conventions).
- **Duplicates two devices create** before they've synced are merged by `SyncDeduplicator`: default categories (at cold launch only — merging hard-deletes, and a sheet left open could hold the row), the profile (oldest kept; every profile `@Query` is sorted by `createdAt`), `UserProgress` (oldest kept, others folded in by `UserProgress.absorb` — max XP, union of awards), `MascotConfig`, `FXRateSnapshot` (newest kept), `BudgetMonthCommitment` (lower of each bucket). Runs at launch, on activation, and after imports (`NSPersistentStoreRemoteChange`, debounced). Two devices editing the same record offline: the last write wins.
- **A second device** checks iCloud before offering setup (`CloudAccountService.hasExistingData`, reading the mirrored zone's change feed — a `CKQuery` would need an index the mirrored schema lacks) and, if a profile is there, waits ("מצאנו את הנתונים שלך ב-iCloud") until it syncs in, with "להתחיל בכל זאת" as the way out. It **re-checks every few seconds** and drops back to setup if the profile disappears — after a DEBUG wipe on this device, the deletions are still uploading when the first check runs — and says so after ~45 s. To test the real thing, **delete the app** (a wipe from the admin panel deletes the dev container's iCloud data too) and reinstall. DEBUG: `-demoCloudWait`.
- **Before a TestFlight / App Store build**: TestFlight uses the **Production** CloudKit environment, which only has schema that was deployed to it. Launch once from Xcode with the **Release** configuration on a device signed into iCloud, with the `-initCloudKitSchema` launch argument (`PersistentStore.initializeCloudKitSchema`, a scratch store — the real data is untouched; the console reports the result), then CloudKit Console → iCloud.com.oshrat.app → Deploy Schema Changes to Production. Repeat after any model change. The app **quits** after the schema run instead of opening the real store: any build run from Xcode is development-signed and syncs with the **Development** environment, so on a phone with the App Store app it would run over that app's store and merge in old test data from Development (it did, once). Afterwards, don't open that Xcode-installed Release app again — reinstall from TestFlight / the App Store.

## Money & data rules

- All monetary amounts use `Decimal`, never `Double` or `Float` (avoids rounding errors).
- Account balances are entered and updated **manually by the user** and are the source of truth for net worth. Transactions are a separate income/expense log that feeds the dashboard and budget — we do **not** auto-recompute balances from transactions in the MVP.
- The data models **sync through CloudKit**: every stored property optional or defaulted, every relationship optional (to-many too) with an inverse, no unique constraints — see *iCloud sync*.

## Data models (SwiftData `@Model` classes)

Define these in a `Models/` group.

Shared enums (String-backed, `Codable`), all in `Models/SharedEnums.swift`:
- `TransactionKind`: `income`, `expense`
- `AccountType`: `current`, `digitalWallet`, `savings`, `investment`. Also carries the per-type `symbolName` (SF Symbol), `sortRank` (dashboard / analytics ordering) and `isLiquid` (the dashboard's נזיל / נכסים split) — use those rather than re-writing the switch in a view. Decodes unknown raw values to `.current`, so a removed case can't brick the whole store (as `.other` once did). **`.investment` is currently blocked in the UI** (see *Investments* below) but still a valid stored value.
- `DepositKind`: `oneTime`, `replenishable` — whether a deposit takes money once or keeps taking it (see *Deposits* below). Stored on `Account` as **`depositKindRaw` (a `String`) with a computed typed view**, the same shape `BudgetItem` uses: a Codable enum attribute added to a model that already has rows in the store traps on read (`swift_dynamicCast` failure inside SwiftData), where a defaulted `String` migrates silently. Decodes unknown raw values to `.oneTime`.
- `CategoryNature`: `need`, `want`, `neutral` (powers needs-vs-wants)
- `RecurrenceUnit`: `day`, `week`, `month`, `year` — the current cadence model ("every N units"). Sub-monthly units average into *every* month; monthly/yearly land their full amount on the months they occur in.
- `BudgetFrequencyKind` / `BudgetScheduleKind` — **legacy**, superseded by `RecurrenceUnit` + a count. Still persisted so pre-existing `BudgetItem` rows migrate cleanly, and `BudgetScheduleKind` still distinguishes `oneTime` from recurring.

Models:
- **UserProfile** — name, profession, free-text goals, preferred currency code, createdAt, and `shiftsIncomeToBusinessDay` (default on). Holds the personal data from onboarding, edited later in Settings.
- **Account** — name, type (`AccountType`), balance (`Decimal`), currency code, lastUpdated, isFavorite; relationships to its transactions (nullify) and holdings (cascade). The manually managed balances. A `.savings` account is a **deposit (פיקדון)**: it also carries `interestRatePercent`, `depositStartDate`, `maturityDate`, `autoPayoutOnMaturity`, `payoutAccount` (a self-referencing nullify relationship, inverse `incomingDepositPayouts`) and `payoutCompletedAt`. All optional/defaulted, all ignored unless the type is `.savings`, and all-empty is a valid open-ended savings pot. `depositTerms` bridges them to `DepositTerms` and `depositLadder` to `DepositLadder` (**read the ladder** — it answers the same questions for both deposit kinds); `isAwaitingPayout(asOf:)`, which the dashboard prompt *and* the "ממתין לפדיון" badge key on, is ladder-based, so a replenishable deposit only comes due once its **last** sub-deposit has. `depositKind` + a cascade `depositTranches` relationship carry the replenishable case; `effectiveMaturityDate`, `openingDepositAmount` and `depositCount` are the derived reads the views use. **A deposit never carries the favourite star** — `AccountType.allowsFavorite` is false for `.savings`, because favourite means *the default account for a new transaction* and a deposit is money you can't spend. Enforced at every write point (`AccountDraft.apply`, `OnboardingViewModel.commit`, `HomeView.onToggleFavorite`) rather than defended per view; `clearFavoriteIfNotAllowed()` heals rows starred before the rule existed, called once from `HomeView`.
- **Holding** — symbol, name, quantity, marketValue (`Decimal`), currency code, lastUpdated; belongs to an investment `Account`. A single manually-valued position (stock/ETF).
- **Category** — name (Hebrew label), kind (`TransactionKind`), nature (`CategoryNature`), colorHex, SF Symbol name, `isUserCreated` (false = a seeded default); relationship to its transactions. **Defaults are read-only; the user's own are editable** (see *Categories* below); `Category.nameIsTaken` is the one-name-per-kind rule the editor enforces, since the launch-time dedupe pass would otherwise merge two same-named rows.
- **Transaction** — amount (`Decimal`), kind, date, title, note, currency code, optional balanceAfter; optional links to a Category and an Account, plus a cascade `attachments` relationship. The income/expense log. A row logged from a scheduled budget line also carries `budgetItem` (nullify) and `budgetOccurrenceDate` — *which* scheduled day it settles, kept apart from `date` (when the money moved, today by default) so logging next week's rent early greys next week, not today. (A "manual balance edit" marker title flags bookkeeping rows so totals can exclude them.) `date` is a full moment, and **`hasTimeOfDay`** (default `false`) says whether its time is real: set by the sheet (whose picker shows hours and minutes, defaulting to now), `PaymentLogger` (the tap) and deposit payouts. Rows from before 1.1 read `false` — their stored time is just when they were typed in — so the expanded card shows no time for them, and editing one offers "הוספת שעה". The list sorts on `date` either way. Demo rows get seeded times (and a wallet top-up lands ten minutes before the spend that needed it).
- **TransactionAttachment** — filename, `@Attribute(.externalStorage)` data blob, typeIdentifier (UTI string), createdAt; belongs to a `Transaction` (cascade). A receipt/invoice the user attached — image or PDF — added from Camera/Photos/Files in the transaction sheet and viewed (via QuickLook) from the expandable transaction card. Camera needs `NSCameraUsageDescription` in `OshRat/Info.plist`.
- **BudgetItem** — optional Category, plannedAmount (`Decimal`), kind, currency code, frequency (`BudgetFrequencyKind`), and an optional **schedule** (`BudgetScheduleKind` + day/month/year, plus an optional month/year **end bound** for recurring lines — "until January 2028"). `plannedAmount(inMonth:year:)` attributes each line to the right month; `occurrenceDate(...)` resolves the calendar day and, for **income**, shifts it off Shabbat *and Israeli holidays* to the next business day by default via `businessDay(onOrAfter:)` + `IsraeliHolidays`. Feeds planned-vs-actual and the budget calendar (which tints Shabbat and holidays). `lastEditedAt` is stamped by `init` and, through the drafts' `apply(to:)`, only when `editableFields` actually changed — the budget achievements use it to know which months' plans can still be captured, and for the old rule on months without a committed plan (deletions go to `UserProgress.budgetLastTouchedAt`). Also carries the inverse `loggedTransactions` and the two budget-reminder stamps, `reminderAnnouncedFor` / `reminderAcknowledgedFor` (start of day; see *Budget reminders*) — both deliberately **outside** `editableFields`, since seeing a reminder isn't editing the budget. `displayTitle` is the line's one-line name (income: source; expense: category — note), shared by the calendar rows and the toast.
- **DepositTranche** — one sub-deposit ("הפקדה") inside a *replenishable* deposit: amount, its own `interestRatePercent` and `maturityDate`, startDate, note, its `account` (cascade) and the `fundingTransaction` that created it (cascade from `Transaction.fundedDepositTranches`). Rates and dates are **copied** from the account at creation, not inherited by reference — terms agreed in March shouldn't change because the account's defaults were edited in June. `isLive` is false while the funding transfer sits in Recently Deleted, which is how a deleted transfer drops its rung out of the ladder and a restore brings it back. The **opening** deposit has no row: it's derived as the remainder (see `DepositLadder`).
- **Goal** — title, targetAmount, savedAmount (`Decimal`), optional targetDate, note, currency code, isCompleted, optional `createdAt` / `completedAt` (the Goals UI must set `completedAt`; `goal-done` needs both). Covers goals and future plans.
- **FXRateSnapshot** — base currency, rates map, fetchedAt. Cached daily exchange rates (see *FX rates* above).
- **UserProgress** — the one XP row: totalXP, currentStreak/longestStreak/lastActivityDate, `awardedKeys` (one-time awards already paid), the daily-cap counter and its date, `pendingCelebrations` (the toast queue, as `Celebration` raw values — `level:N`, `achievement:<id>`, `achievements:N`; `pendingLevelUpLevel` is its legacy predecessor, moved into the queue on first read), the last-award marker, and the achievements state: `unlockedAchievements` (ids, the patch ledger), `achievementsEpoch`, `budgetLastTouchedAt`; `quietDays` (see *Evening reminder & quiet days*) and `lastCelebrationAt` (see *Mascot mood*). Only *progress* is stored — what earns XP and what a level costs are code constants in `XPRules`, so rebalancing is an edit, not a migration. See *Gamification* below.
- **MascotConfig** — what the user's rat wears: one optional equipped item id per wardrobe slot (`backgroundID`, `outfitID`, `glassesID`, `hatID`, `propID`, `pantsID`, `shoesID`), all `nil` for the Bare rat everyone starts as. One row, resolved oldest-first by `WardrobeService.config(in:)`. Unlocks are *not* stored — they derive from the level.

Not a `@Model`, but part of the same layer:
- **XPRules** (`Models/XPRules.swift`) — the single tunable config (XP amounts, the daily cap, streak milestones, the level curve) plus the pure maths: `level(forTotalXP:)`, `totalXP(toReach:)`, `progress(forTotalXP:)` → `LevelProgress`, `nextStreak(...)`, `cappedAward(...)`. Also holds `XPReason`, whose raw values are persisted — add cases, never rename them. Unit-tested (`OshRatTests/XPRulesTests.swift`) and compiled into the test targets — see the pbxproj gotcha below.
- **Achievement** / **AchievementEvaluator** (`Models/`) — the 24-entry catalogue as code (`id` is persisted — never rename) and the pure rules: an `AchievementSnapshot` of plain values in, satisfied ids out. `ProgressService` builds the snapshot; month money verdicts come from `BudgetVsActual`, never reimplemented. Tested in `OshRatTests/AchievementEvaluatorTests.swift`; both files are in the test targets.
- **WardrobeItem** (`Models/WardrobeItem.swift`) — the wardrobe catalogue as code: id (persisted in `MascotConfig` *and* the asset-name stem, so never rename), Hebrew name, `WardrobeSlot`, tier (the achievement metals), `unlockLevel` and `coversLimbs` (false for the sleeveless puffer vests and the legless skirts). `bodyAssetName(on:)` / `limbAssetName(_:on:)` name its layers per canvas (`AvatarCanvas`). Adding an item is one catalogue line plus its SVG layers. Tested in `OshRatTests/WardrobeCatalogTests.swift`; in the test targets.
- **DepositTerms** (`Models/DepositTerms.swift`) — the pure, unit-tested term maths behind a deposit: `isMatured`, `daysRemaining`, `progress`, `value(asOf:)`, `projectedValue`. **Simple annual interest** (`principal × (1 + rate × years)`, 365-day years), not compounding: the user can reproduce it on a calculator, and the payout prompt lets them overwrite it with the bank's real figure anyway. Accrual stops at maturity. Compiled into the test targets as well as the app — see the pbxproj gotcha below.
- **DepositLadder** (`Models/DepositLadder.swift`) — the pure, unit-tested sum of a deposit's sub-deposits: total principal, `value(asOf:)`, `projectedValue`, and a `maturityDate` that is the **latest** rung's (nil while any rung is open-ended, so a deposit still taking money never prompts). A one-time deposit is a one-rung ladder, so every screen reads the ladder and stops caring which kind it is. `make(balance:opening:additions:)` reconciles the rungs against the account balance: the **opening deposit is the plug** (`balance − Σ additions`, never stored, so it can't drift from the balance a hand-correction or a deleted transfer just moved), and when the additions exceed the balance the shortfall comes off the **newest** end. Also in the test targets.
- **CategoryBudgetStatus** (in `Models/BudgetItem.swift`, so the test target already compiles it; tested in `OshRatTests/CategoryBudgetStatusTests.swift`) — one category's month, planned vs actual, for the bar in a transaction's expanded card. Counted by `BudgetVsActual`'s rules, narrowed to a category: every budget line of it adds `plannedAmount(inMonth:year:)`, every real row of it in the month adds its amount (transfers and manual balance edits out), both in the preferred currency with unconvertible rows skipped and flagged. `nil` when nothing is planned. `make` expects the ledger **newest first** and stops at the first row before the month, so opening a recent transaction reads a month of rows rather than the whole history — it runs on the card's opening frame. Months are Gregorian, as `BudgetItem`'s are.

Register every model in `OshRatSchema.models` (`Services/PersistentStore.swift`) — the one list the app's container and every preview are built from. **Stored changes must be additive** (a new model, a new optional or defaulted attribute, a new optional relationship with an inverse): a CloudKit-mirrored store only supports lightweight migration, which SwiftData does by itself from the model cached in the store, so there is no versioned schema or migration plan (a staged V1/V2 plan existed briefly and was dropped; stores written under it open unchanged). Never rename or remove a stored property or make an optional one required — the deployed CloudKit schema can only grow. Verify a change by launching over a store the previous build wrote (the simulator's dev data is one). **A store that won't open never crashes the app**: `PersistentStore` turns the failure into a state, and `OshRatApp` shows `StoreRecoveryView` (retry / share a copy of the files / start fresh, which *moves* the old store into `Application Support/Recovered Stores/<date>` rather than deleting it). With iCloud signed in, "start fresh" re-downloads what was synced.

## Features (build order)

MVP, roughly in this order (1–3 implemented; 4 not yet):
1. **Onboarding / setup wizard** — collect personal data → financial accounts (current, investment) → budget (planned income & expenses). **The budget step is optional, income included** — the app is about managing spending and not everyone has a fixed income to plan. `OnboardingViewModel.canContinue` is always true there, and the last button reads "דילוג וסיום" while both lists are empty (`isBudgetEmpty`). Everything downstream copes with no plan: the dashboard card falls back to actuals only (its empty state points at the pencil), a bucket with nothing planned shows no percentage, and the overrun alert needs a non-zero expense plan. Keep it that way — don't reintroduce a required budget line. Seed a default set of Hebrew income/expense categories on first launch (`SeedData`, see *Categories*). **A half-finished wizard survives the app being closed**: every change is saved as an `OnboardingProgress` snapshot (`ViewModels/OnboardingProgress.swift`) to `UserDefaults` — deliberately not SwiftData, since a `UserProfile` row is what routes to the dashboard and nothing may reach the store before "סיום". The next launch's `WelcomeView` then greets the user back and offers "המשך בהגדרה" (with "להתחיל מחדש" behind a confirmation). Budget lines save their category by **name + kind**, not a store reference, so a vanished category drops that line instead of trapping. The snapshot is cleared on commit, on a fresh start, and by `DemoDataService.wipe`. A form still open in an editor sheet isn't covered — it isn't in the view model yet.
2. **Dashboard** — a clean, minimal, friendly summary: net worth, this month's income vs expenses, budget progress (month-aware), goal progress. The assets card splits its rows into **נזיל** (עו״ש + ארנק דיגיטלי) and **נכסים** (פיקדונות + השקעות) by `AccountType.isLiquid`, each with its own subtotal under the combined total. Rows are **capped at the first three** (a "הצג עוד" toggle at the card's bottom-left opens the rest) so the card can't push the budget card off-screen; collapsing hides *rows only* — each group header still subtotals every account in it, so the parts keep adding up to the hero total.
3. **Transactions** — add / edit / delete income and expenses (and transfers) anytime, each with a category and account. **Multi-select**: long-press a row to enter selection mode, tap to add rows, "בחירת הכול" takes everything the current filters leave on screen (not the whole store), and the bar's trash soft-deletes the batch behind one confirmation. Selection mode collapses any open insights card and disables the row swipes, so a tap means one thing at a time. **Copy**: the row's *leading* swipe (visual right, swiping left; full swipe fires it) opens `NewTransactionSheet(copying:)` titled "העתקת תנועה" — kind, accounts, category, title, note, amount and currency carry over (transfers copy as transfers), but the **date is today**, and **attachments** and the **budget-occurrence link** are deliberately left behind (a receipt belongs to its purchase; a second link would count the occurrence twice). A soft-deleted account isn't copied — `primeDefaults` re-picks it, and a transfer re-picks a missing destination — and the amount keeps its currency even when the account is re-picked (the same `old == nil` guard the budget link uses). Manual balance edits have no copy swipe. The expanded card opens with the row's time ("בשעה 14:32", 24-hour) when it has one. **Filters live in `TransactionFilters`** (`ViewModels/`), owned by `HomeView` — `HomeView` rebuilds each tab branch on switch, so filters held in the list's own `@State` were wiped by a glance at the dashboard. Session-scoped, deliberately not `@AppStorage`: a filter set last week that silently hides most of the ledger on a cold launch is a bug report waiting to happen. The rest of the list's design is in the bullets below.
   - **Filters & sort** (`TransactionFilters`, tested in `OshRatTests/TransactionFiltersTests.swift`). Each active filter is its own removable chip in `ActiveFiltersBar` under the search field — type, category, dates — plus "ניקוי הכול" once two or more are on; a single "reset everything" chip used to throw away a carefully picked category along with a date range. Chips appear without animation on purpose: the same change reshapes the list, and an animated diff of a page of rows hitches. The sheet's dates are a one-tap `DatePresetGrid` (adaptive columns on a `@ScaledMetric` width, so large text drops columns rather than truncating) of **calendar** presets (החודש / החודש שעבר / השנה — how a budget is read) and **rolling** ones (7 / 30 / 90 days), with the resolved days captioned (`rangeDescription`); "טווח מותאם" is `beginCustomRange()`, which seeds both pickers from the window already showing and caps the end at today. Every window is **whole days, half-open** (`start <= date < end`) — a rolling window cut at the current time of day left the oldest day's group half-empty — and cut in a **Gregorian** calendar, since a device set to the Hebrew calendar would otherwise make "this month" a Hebrew month. The sheet opens at a `.fraction(0.7)` detent: `.medium` cut the date grid off, and 0.7 keeps the chips visible above it so each tap shows up live. **Sort** (`TransactionSort`) is a toolbar `Menu` beside the filter button, sharing its glass group. It is *not* a filter: it's outside `hasActiveFilters` and survives `clear()`. It runs once per render, after filtering; the date orders are free (as delivered, or reversed), and the amount orders rank in the preferred currency (`rankingAmount()`, one FX factor per currency — `FXRateSnapshot.rates` re-decodes JSON on every access) on a `(Double, index)` key, which took a 20,000-row ranking from ~140 ms to ~34 ms. Amount orders drop the day headers (every row would get one) and rows show their own date instead. Because sorted order isn't date order, a similar-transaction jump to a row the filters hide can't read its position off `allTransactions`: it sets `pendingJumpID`, clears the filters, and finishes in `onChange(of: resetKey)` against the real rows.
   - **Expanded card** (`ExpandedTransactionCard`). The card is **its own `List` row**, inserted after the transaction's (`row(_:proxy:)` is a `@ViewBuilder` yielding two rows) — never extra height on the tapped row.    - **Search** (`ViewModels/HebrewSearch.swift`, `ViewModels/TransactionSearchIndex.swift`, tested in `OshRatTests/TransactionSearchTests.swift`; both files are in the test target alongside `TransactionFilters`). Covers title, note, category, **account names** and the **amount** (plain digits, so "120" finds ₪120.50). `HebrewSearch.fold` is the one canonical form for query and haystack: lowercased, niqqud dropped, **final letters folded** (ן→נ…), geresh/gershayim and quotes removed, other punctuation → space. Every query word must match somewhere (AND), and each match is tiered by `SearchMatchTier`:
     - **exact** — the folded text contains the token;
     - **spelling** — the vowel-less *skeleton* matches (ו/י dropped after the first letter: תוכנית ↔ תכנית);
     - **typo** — within a weighted edit distance of a word or its prefix (so a half-typed word already matches). Budget by length: ≤2 letters exact only, 3 → 0.5, 4–6 → 1, 7+ → 2; a substitution between **neighbouring keys on the Hebrew keyboard costs 0.5** (so "יקקן" finds "ירקן" — ק sits beside ר). Numeric tokens are never typo-matched.
     A query with Latin letters is also tried as if typed on the **Hebrew layout** ("hrei" → ירקן). `TransactionFilters.results` returns typo matches **only when nothing matched exactly or by spelling**, with `isApproximate` set so the list says "לא נמצאה התאמה מדויקת — מוצגות תוצאות דומות" — mixing them in would bury the real hit under every word one letter away. `TransactionSearchIndex` caches each row's folded words and rebuilds an entry only when its raw source strings differ, so edits and renamed accounts need no invalidation; it lives `@ObservationIgnored` on `TransactionFilters` (a cache filled during render mustn't schedule another render) and prunes orphans once they outnumber live rows. The view applies the search through a ~180 ms debounce (`appliedSearch`, a `task(id: filters.search)`); clearing applies at once.
   - **List performance** (`Views/Transactions/TransactionsListView.swift`) — it was glitchy on a long ledger, and each of these fixed a measured cost:
     - **Filter once per render.** `body` computes `filters.results(...)` into a `let` and passes it down. It used to be a computed property read from three places, so every render filtered the ledger several times over.
     - **The parent/child split.** `TransactionsListView` owns the query, the search field and the filter pass; the private `TransactionLedger` owns everything that changes while browsing — expanded row, jump highlight, multi-select, the page size. State that changes on a tap must live in the child, or the tap re-runs the whole filter pipeline.
     - **Paging.** The ledger mounts `pageSize` (120) rows; a `ProgressView` footer, re-identified by `.id(rowLimit)` so it fires again if still on screen, mounts the next page. `List` builds row *views* lazily but re-diffs every row *identity* on every update. Reset on any `LedgerQueryKey` change. "בחירת הכול" still selects every matching row, mounted or not, and a similar-transaction jump raises the limit to reach its target first.
     - **No per-row faults.** The `@Query` is a `FetchDescriptor` with `relationshipKeyPathsForPrefetching` for category/account/destination, and the paperclip comes from one `TransactionAttachment` query (`propertiesToFetch = [\.transaction]`) turned into a set of ids. Reading `transaction.attachments` in a row fires a to-many fault per row as it scrolls — including small blobs stored inline — so don't bring it back.
     - Day groups are built in one linear pass: under a date order the rows arrive date-sorted (as queried, or reversed), so there's no dictionary to build and nothing to re-sort. An amount order renders one headerless group.

Things learned on a real phone, each of which broke it:
  - **The action runs in the background and leaves a notification** — it must not open the app. The automation fires with the phone usually still locked and the payment sheet on top, and an intent that brought the app forward failed there with an error. Now it parks the payment and posts a local notification ("₪42.90 · Cafe Nero", `PaymentNotifier`); tapping it opens the app, and `HomeView` shows the waiting payment (and clears its notification). Notification permission is asked for on the setup screen (`PaymentNotificationsRow`), since the intent runs where no prompt can appear. `PaymentNotifier` is also the notification centre's delegate (set in `OshRatApp.init`) and hides the banner while the app is open, where the sheet comes up by itself.
  - **The action runs in an App Intents extension when the app isn't running** (`OshRatIntents/`, an ExtensionKit target embedded under `Extensions/`). `LogPaymentIntent.swift` is compiled into the app **and** the extension: the system runs it in the app when the app is running and in the extension otherwise, and keeping it in the app keeps the action's identity, so automations built earlier still find it. The extension compiles only `LogPaymentIntent`, `PaymentPrefill` (the value, parsing and setup check — the history matching is `PaymentPrefill+History.swift`, app-only), `PaymentInbox` and `PaymentNotification`; anything the intent touches must compile there — **no models, no `IncomingPaymentRouter`**. Why: cold-launching the whole app at the till (store, CloudKit, `SyncDeduplicator`) sometimes ran out of the time Shortcuts allows. The app's own background launches stay light for the same reason — **nothing opens the store in `OshRatApp.init`**: `PersistentStore.shared` opens lazily, from the `WindowGroup`'s content (`StoreGate`) or `DailyReminderService.container`. If the notification can't be posted the intent **throws** `LogPaymentError`, whose message Shortcuts shows as a banner; it also throws if the App Group is unreachable, rather than save where the app can't see. A payment with no details gets a "check the setup" notification body.
  - **Waiting payments are on disk, in the App Group** (`PaymentInbox`, JSON in the group's `UserDefaults`; `PaymentPrefill` is `Codable`) — the process that ran the intent is often gone by the time the notification is tapped, and may have been the extension. **Two processes write it**, so every change goes through `PaymentInbox.update` (re-read, change, write back — never write a copy held in memory, which would erase a payment the extension appended), and each write posts a Darwin notification the app observes. `IncomingPaymentRouter` is the app's observable mirror of it; a payment id this launch hasn't seen counts as an arrival (ends a snooze), a put-back one doesn't. Payments queued by builds before the App Group are moved in once (`migrateFromAppDefaultsIfNeeded`, from the router's `init`). Tested in `PaymentPrefillTests`. On the simulator, `simctl spawn … defaults write <bundle-id>` writes the simulator's global preferences, **not** the app's sandbox — it can't seed this queue. A payment is kept for `PaymentPrefill.freshness` (a week). `ContentView` skips the login screen while one waits and re-reads the queue when the app becomes active.
  - **The amount parameter is text, not `IntentCurrencyAmount`**: the Wallet trigger's amount arrives formatted for the device ("‏42.90 ‏₪"), a typed currency parameter came through empty, and `PaymentPrefill.parseAmount` reads the number and currency out of any of those shapes (tested).
  - **The action must be added to a new shortcut in the automation** ("New Shortcut" after "Next"), not picked ready-made from the list there (that adds it with empty fields and nowhere to connect them — why the app no longer declares an `AppShortcutsProvider`), and **a shared iCloud shortcut doesn't work**: a standalone shortcut's input types ("Apps and 18 more") exclude a Wallet payment, so the automation handed it nothing. Tried and dropped.

(A sheet per payment closed between each, and in the gap the XP toast appeared, even after a cancel.) "ביטול" discards a payment; a swipe-down puts the one on screen back and leaves the line for later — `HomeView` snoozes it (`arePaymentsSnoozed`, set as the sheet opens) until a new payment arrives (`IncomingPaymentRouter.arrivals`) or the app comes back to the front. **"דילוג"** (toolbar, queue mode) parks a payment instead (`skippedAt`): it no longer comes up by itself, and `PendingPaymentsListRow` at the top of the transactions list counts every waiting payment — tapping it (`IncomingPaymentRouter.requestReview`) un-parks them and brings the line up. A payment still unlogged after `PaymentPrefill.freshness` (**a week**) is deleted, notification and all (`removeExpired`, on every activation). The banner also offers **"רישום כולם"**, which logs only the up-next ones; skipped payments stay parked. That logs every waiting payment that is *complete* (amount, title, category and an account the amount can be booked in, i.e. what `canConfirm` demands, resolved from earlier payments at the same shop) through `PaymentLogger` (dated when the card was tapped, balance moved like the sheet does), puts the incomplete ones back at the front of the queue (`takeAll` / `putBack`), then saves the one on screen if it is complete, or leaves it open with a note as the first one needing the user. ## Gamification (XP core)

Phase 1 of `GAMIFICATION.md` is built, and so is phase 2's **engine** (per `ACHIEVEMENTS.md`) plus the profile shelf that draws the patches, and phase 3's wardrobe with hats, glasses, tops, pants and shoes unlocking by level; phase 4 (polish) is not. The full plan, including the layered-SVG mascot design, lives in that file — this section is just how the shipped part works.

- **`ProgressService` is the only thing that awards XP**, and it's called from the app's existing write points, never from a view's own logic: `NewTransactionSheet.handleConfirm` (new rows only — an edit is not new activity, or re-saving a row would farm points), `AccountDraft.apply` (on a real balance change) and `OnboardingViewModel.commit` (the setup milestones). Every entry point saves, so callers don't have to remember to.
- **All judgement lives in `XPRules`**, which is pure and tested. The service only reads and writes the store. To rebalance the game, edit the constants at the top of `XPRules` and nothing else.
- **Farmable actions share one daily cap** (`dailyUsageCap`), not one cap each — separate caps just move the farming around. It clamps rather than refuses, so an award at the boundary pays what's left. One-time and streak awards are never capped.
- **One-time awards are keyed** in `UserProgress.awardedKeys` (an `XPReason` raw value for setup milestones, `streak-7` for streak rungs), so a milestone can't pay twice — including a user who lapses and climbs back to the same streak.
- **The streak follows logging, not app-opening** (the plan's first principle). **The weekend and chagim can't break it**: a gap whose skipped days are all rest days (`XPRules.isStreakRestDay` — Friday/Saturday via `streakRestWeekdays`, plus the rest-day holidays from `IsraeliHolidays.isBankHoliday`, the same ones that move a salary) still extends the streak — Thursday → Sunday is +1 — while logging on a rest day counts like any day. A skipped working day still resets it, working-day holidays (Hanukkah, Purim) included. A lapse resets the streak and *never* the XP, and the card says "מתחילים רצף" rather than "0 days" — nothing in this system punishes or nags.
- **Celebrations are announced through the store, not a return value.** Level-ups and unlocked achievements are appended to `UserProgress.pendingCelebrations` in the order they happened (a patch, then the level it pushed you to); `HomeView` shows the head as `CelebrationToast` and `ProgressService.dismissCelebration` pops it once the toast has animated out. The XP that triggers one is usually earned inside a sheet that's already dismissing itself, so the celebration has to outlive the screen that caused it — and one earned just before the app was killed still fires on the next launch. The toast waits while any sheet or alert presented from `HomeView` is up (an overlay sits *under* them), and a cancelled run leaves the queue alone so it replays. A pass that unlocks more than `ProgressService.celebrationBatchThreshold` (3) patches queues one "פתחת N הישגים חדשים" toast plus only the level it ended on, instead of a toast each. Tapping an achievement toast opens the profile tab.
- **Sound and haptics** (`Services/CelebrationFeedback.swift`): moments rising in size — a new transaction (one warm tone, played from `NewTransactionSheet.handleConfirm` for new rows only), the XP it earned (`xp-gain.caf`, Kenney `maximize_006`: a low sweep rising about an octave, played by `XPGainToast` as its bar starts to fill, quieter than the transaction tone it follows — the brighter `maximize` sweeps are hissy), an achievement (a two-note steel-drum phrase: `STEEL04` for bronze/silver and the batch toast, `STEEL08` for gold) and a level-up (four plucked-string notes), the last two played by the toast as it slides in. The **budget reminder** is a fourth, separate moment — a nudge, not a reward — so it is deliberately *not* a chime: one solid bell strike (Kenney `bong_001`, `reminder-budget.caf`) with one full, low-sharpness tap. The sounds are **CC0 assets by Kenney**, fetched and prepared by `Scripts/prepare_sounds.py` (credits in `Scripts/SOUNDS_CREDITS.md`) into `OshRat/Sounds/` (each pick names its output file). Two synthesised versions came before them and both were rejected as sharp and cheap — don't go back to generating sounds. Haptics are **crisp transient taps only**, one per note, timed to the onsets the script prints and building to a clearly stronger last tap (Apple's "success" shape); a continuous low-sharpness swell was tried and felt like a cheap buzzer. The audio session is `.ambient`, so the silent switch mutes them and other audio keeps playing; Settings → "צלילים ורטט" turns sounds and haptics off (`CelebrationFeedback.isEnabledKey`). The simulator plays neither haptics nor reliable audio — judge them on a device.
- **Achievements are evaluated from facts, not the XP ledger** — `ProgressService.evaluateAchievements` runs at the end of every entry point, on dashboard appear (catches month closes) and after a deposit payout. It is retroactive: an existing user unlocks what they've already done, patches *and* XP. Anti-farming keys on `Transaction.createdAt` (entry time, stamped by `init`; `nil` = legacy row, counted in totals but never as a spread day), never on the user-chosen `date`. Budget months are only judged after `achievementsEpoch`, and **against the month's own committed plan** (`BudgetMonthCommitment`, kept by `BudgetCommitmentService`): each month's planned needs and wants are written down when it begins (captured on every evaluation, for months the budget hasn't changed since), and a budget change — which goes through `BudgetCommitmentService.change` in the budget editor and the calendar — can only *tighten* the current month (`PlannedSpend.tightened`). So adding a forgotten line, planning a future bill or raising a limit mid-month costs nothing, cutting one makes the month harder, and a later edit can't reach back to a closed month. A month with no commitment keeps the old rule: only if no budget line changed since before it began. `PlannedSpend` is also the rule `BudgetVsActual.hasOverrun` uses, so the card and the verdict agree. `BudgetMonthCommitment` is an ordinary synced model (an additive, lightweight change).
- **`LevelProgressCard`** lives on the **profile tab** (`Views/Profile/ProfileView.swift`): level, a bar to the next level, the streak, and what the last points were for (the plan's "always show *why* XP was earned" guardrail, standing in for an XP ledger that phase 1 doesn't have). It sat on the dashboard until the profile tab existed to hold it.
- **`XPLevelBadge`** is what the dashboard kept: a capsule that fills with `LevelProgress.fraction` and carries "רמה N" **inside** it. It rides the **assets card's top edge** at the visual left, opposite the greeting mascot resting on the other end of the same edge — parked there by an `.overlay(alignment: .topTrailing)` on the card whose `.top` alignment guide is redefined as `$0[.bottom] + Theme.Spacing.md`, so its base **hovers** a fixed 16pt above the card's edge. Doing it with an alignment guide rather than a negative `.offset` means the badge's Dynamic-Type height never has to be guessed at from `HomeView`, and the gap holds at every text size. Display-only: the rat in the bottom bar is the single way into the profile, so the badge isn't also a button. Both it and `LevelProgressCard` read `progressRows.first`, so they can't disagree. Three details that are load-bearing: the base is **opaque** (`Theme.Colors.surface`) so it reads as a solid chip rather than a tinted patch of the page, and its shadow is what lifts it off the page; the charge is a **`Rectangle` clipped to a `Capsule`**, not a second `Capsule`, because a rounded growing edge makes it read as a toggle switch; and the label is `textPrimary`, not the accent, because it sits over the fill on one side and the empty track on the other and has to clear 4.5:1 on both. `ZStack(alignment: .leading)` mirrors under RTL, so the charge grows from the visual right.

## Navigation

- `ContentView` routes by data: no `UserProfile` in SwiftData → `OnboardingFlowView`; otherwise the **login screen** (`Views/Login/LoginView.swift`, button "לחשבון שלי") and, once entered, `HomeView`. There's no "did the user onboard?" flag — the data is the source of truth. The login is a front door, not authentication (the data never leaves the device): entry is per launch (`@State`), and it's skipped when the app was opened to do something — the widget's link (which `ContentView` receives and parks in `DeepLinkRouter` for `HomeView`) or a pending Apple Pay payment — and right after the wizard finishes. It shares its look with the first-launch welcome through `BrandHeroLayout` + `HeroPrimaryButton` (`Views/Onboarding/`), so the two can't drift apart. DEBUG: `-demoTab`, `-demoWardrobe` and `-skipLogin` skip it; `-demoScenario` alone lands on it.
- `HomeView` is the app shell. It owns the shared chrome — background, the floating glass `HomeBottomBar`, the FAB (new transaction), and the global sheets (new transaction, budget editor, account editor) — and switches between tab branches on a `@State selectedTab: HomeBottomBar.Tab`.
- `HomeBottomBar.Tab`: `home` (raised center button sitting in the notch), `profile`, `transactions`, `analytics`, `calendar` — **two per flank**, so the notch stays centred between equal groups. Right-to-left on screen that reads rat, תנועות, (home), תובנות, יומן. The calendar icon wears a small bell badge (`ReminderBadge`, at `.topTrailing` — visual top-left under RTL) while a budget reminder is pending. Side icons are `HomeBarButton` (brand accent when selected, secondary otherwise); the center is the raised `HomeCenterButton`. The bar is built on the iOS 26 `glassEffect` with a custom `NotchedBarShape`.
- **`HomeBarButton` is generic over its icon**, not a symbol name, because one of the four isn't a symbol. It applies the tint to the *container*, so an `Image(systemName:)` and a bare `Shape` (which fills with the foreground style) colour identically with nothing to remember per call site. The three symbol tabs go through `BarSymbol` so they can't drift apart typographically.
- **`RatHeadShape`** is the profile tab's icon, drawn by hand next to `NotchedBarShape`: SF Symbols has no rat or mouse **animal** glyph (only `computermouse`, `hare`, `pawprint`, `tortoise`), so the app draws its own. It is a **whole rat in profile — crouching, nose to the visual left, tail sweeping up over its back — not a head**, and that is the point: any front-facing rodent head is two lobes above a face, which is the Mickey silhouette, near enough to be someone else's mark. Tilting the ears into ovals, dropping them to the temples and lengthening the muzzle were each tried and each still read as it; the lobes are the tell, not the face under them. Four further things are settled and shouldn't be re-litigated:
  - **Filled, not stroked.** Two attempts at line art failed at ~21pt: the ear lobes merged into the skull's outline and the inner-ear detail read as a pair of *eyes*.
  - **A custom `Shape`'s coordinate space is mirrored under RTL** — confirmed on device, not assumed: drawn nose-left it rendered facing *right*, off the screen edge. The coordinates are pre-mirrored so it faces into the bar.
  - **Every subpath is wound clockwise**, verified by signed area rather than by eye, because `fill` uses the nonzero rule and a disagreeing subpath cancels the overlap into a hole. Mirroring flips winding, so each path is also traversed in reverse to put it back — which is why the curves read tail-first. `addEllipseClockwise` emits the ear to match (`Path.addEllipse` winds the other way and can't tilt).
  - **The tail stays thick.** A naturalistic thin one aliases into a stray wisp at 25pt.
  Authored in a 100×100 box and scaled uniformly, so it survives Dynamic Type and a larger rendering needs no second set of numbers.
- The dashboard branch is a plain `ScrollView`; each other tab is wrapped in its **own** `NavigationStack` inside `HomeView`, so it gets its own title + toolbar. **Every tab uses `.navigationBarTitleDisplayMode(.large)`** — תנועות, תובנות, יומן התקציב and הפרופיל שלי read the same way; sheets (filters, editors, Recently Deleted) stay `.inline`. A large title brings its own vertical space, so a screen under one keeps its own top padding minimal rather than stacking a second gap on top. **Bottom clearance on a scrolling screen:** pad with one of the two constants on `HomeBottomBar` (as `.padding(.bottom,)` on a `ScrollView`'s content, or `.contentMargins(.bottom, …, for: .scrollContent)` on a `List`). Pick by what sits at the *end* of the screen:
- `floatingButtonClearance` (~163pt) when the last element is **interactive** — the calendar's "הוספת פריט ליום זה" button, the transactions list's rows (tap to expand, swipe to delete). Clears the bar *and* the floating "+".
- `barClearance` (~98pt) when the last element is just a **card** with nothing tappable at its bottom edge. The "+" may hover over that edge; padding it out costs a chunk of dead space at the end of every scroll.
- **The dashboard is the exception**: it's a plain `ScrollView`, *not* inside a `NavigationStack`, so the bar's `safeAreaInset` **does** reach it. It pads only `Theme.Spacing.md`; `barClearance` there counted the bar twice (measured ~166pt of empty page under the budget card).

Both are full clearances measured from the screen edge. `HomeView` does install the bar as a `safeAreaInset`, but **that inset does not reach the scroll views inside the tab branches** (each sits in its own `NavigationStack`, under a `ZStack` whose background ignores the safe area) — screens measured on the assumption that it did ended up with their last row under the bar. Don't subtract it.
- The dashboard's budget card is a **horizontally paged `ScrollView`** (`BudgetCardCarousel`) — one card per period, swiped to move month-to-month or year-to-year. A nested scroll view on the perpendicular axis is the deliberate choice: it separates the axes *natively* (UIKit locks a pan to whichever direction it starts in), which a custom `DragGesture` cannot — an earlier drag-driven version fought the dashboard's vertical scroll. It bleeds full-width and restores the gutter as `contentMargins`, so pages match the width of the cards above. See the paged-`ScrollView` gotcha in Conventions before widening its window.
- **Widget entry point:** `ContentView` receives the `oshrat://new-transaction` URL (`DeepLink`, shared with the widget), skips the login and parks it in `DeepLinkRouter`; `HomeView` opens the new-transaction sheet once nothing else is presented.
- Feature-local sheets (income/expense editors, the schedule section, calendar add) are presented from within their own screens, not from `HomeView`.
- **To add a tab:** add a case to `HomeBottomBar.Tab`, a `HomeBarButton` (with its icon as a trailing closure) in the bar's `HStack`, and a branch in `HomeView`'s `switch` — then register any new screen files in the pbxproj (see Conventions). `-demoTab <case>` picks it up for free, since `HomeView.initialTab` parses `Tab(rawValue:)`. The flanks currently hold two icons each; a sixth tab means re-balancing them, not appending.

## Settings

`Views/Settings/SettingsView.swift` ("הגדרות"), pushed from the **gear** in the profile tab's toolbar — the one button there. A system `Form` (grouped rows, switches, pickers that read right under RTL and at every text size), tinted with the accent. **Keep it terse**: no footers or explanatory paragraphs — every explanation sits behind a small **i** (`InfoButton`, a borderless button whose popover shows as a bubble via `presentationCompactAdaptation(.popover)`), placed inside a `Label`'s title rather than beside the `Label`, which would lose the icon's spacing. Sections, top to bottom:

- **פרטים אישיים** — name, profession, goal and preferred currency, bound straight to the `UserProfile` (`@Bindable`; SwiftData saves as you type). Each field is a small grey label with its value underneath, because a filled field's placeholder disappears. Leaving with the name emptied puts the old one back — a blank name breaks the greeting and the profile header. Changing the preferred currency only re-rolls the dashboard's totals; nothing stored is converted.
- **תקציב → "הכנסות ביום עסקים"** (`UserProfile.shiftsIncomeToBusinessDay`, default on). Recurring *income* lands on the next business day, skipping **Shabbat** (Israel works Sun–Fri) **and Israeli rest-day holidays** — a salary on the 1st shows on the next open day when the 1st is a Saturday, Yom Kippur, etc. Holidays come from `IsraeliHolidays` (computed offline from the Hebrew calendar): only **rest-day** holidays (yom tov + Independence Day, with its Fri/Sat/Mon observance shift) move a salary; working-day ones (Hanukkah, Purim, Tu BiShvat, Lag BaOmer) are display-only. Implemented in `BudgetItem.occurrenceDate(..., shiftIncomeToBusinessDay:)` + `businessDay(onOrAfter:)`; the setting is **passed down, never read globally** — `BudgetCalendarView` (dots and day rows) and `HomeView`'s reminder check hand it to `BudgetReminderService.occurrence` / `dueItems`, which stay pure. Expenses never move. Known edge: switching it moves an income occurrence to a different day, so one already logged on the old day shows as unlogged on the new one. Tested in `OshRatTests/BusinessDayShiftTests.swift`.
- **רישום מ-Apple Pay** — what it does (behind the header's i), the step-by-step guide (`ApplePaySetupView`) and a "פתיחת קיצורים" link. The new-transaction suggestion has **no switch here** by choice; once the popup's "אל תראה לי שוב" turns `ApplePayTip.enabledKey` off, it stays off.
- **תזכורת ערב** (`DailyReminderService.isEnabledKey`, default on) — the 19:00 working-day reminder; links to the system notification settings when permission is denied.
- **צלילים ורטט** (`CelebrationFeedback.isEnabledKey`, `UserDefaults`, default on) — gates every sound *and* haptic in `CelebrationFeedback.play`. The silent switch still mutes the sound on its own.
- **שערי חליפין** — when the cached rates were fetched, and "רענון עכשיו" (`FXRatesService.refreshNow`): the same single Frankfurter call as the daily refresh, just forced — inside the network exception, not an expansion of it.
- **ניהול** — "הקטגוריות שלי" (pushed) and "נמחקו לאחרונה" (a sheet: `RecentlyDeletedView` brings its own `NavigationStack` and "סיום").
- **אודות** — version and build.

Device-level preferences (sounds, the Apple Pay suggestion's opt-out) live in `UserDefaults`; anything about the user's money or data lives on `UserProfile`. Not built: a data reset for release builds (the wipe is DEBUG-only, in the admin panel), and the planned Pro switches. iCloud has a status row, not a switch — see *iCloud sync*.

## Conventions

- Group code as: `Models/`, `ViewModels/`, `Views/` (with a subfolder per feature), `Services/`, `DesignSystem/`. Visual constants (colours, spacing, typography, `.cardStyle()`) live in `DesignSystem/Theme.swift` — use them, don't hard-code. Shared controls live there too: `PickerRowLabel` is the bordered "opens a `Menu`" row used by the transaction sheet's account/category pickers and the budget editor's category picker, so a "choose one" control looks the same everywhere. Every **category** menu fills it with `CategoryMenuContent` (income, then expenses grouped צרכים / מותרות / אחר, alphabetical by Hebrew collation, each with its glyph) — the transaction sheet, the budget expense editor and the transactions filter all use it, so never hand-roll a category list.
- **Required fields:** a form's save stays **tappable** rather than `.disabled` while something required is empty. A refused tap sets the form's `showsMissingFields`, calls `MissingFields.signalRefusedSave()` (warning haptic + VoiceOver line), and each empty required field shows a red "חובה" via `.missingFieldBadge(showsMissingFields && isEmpty)` (`DesignSystem/MissingFieldBadge.swift`) beside its label, or beside a text field opposite its placeholder. Badges appear only after an attempt and clear as each field fills. The slide-to-confirm reports the attempt through `onBlockedAttempt`. A block that isn't a missing field (no FX rate, a taken name) keeps `.disabled` and its own explanation.
- **Soft delete vs hard delete (crash trap).** Almost everything in the app soft-deletes — `deletedAt` is stamped, the object stays perfectly valid, and a row may safely hold its `@Model`. `RecentlyDeletedView` is the *only* screen that hard-deletes, and `modelContext.delete` invalidates the object **immediately** while SwiftUI keeps the outgoing row alive to animate it away. A row that reads `transaction.title` (or worse, walks `transaction.category?.name`) during that animation traps with "This model instance was invalidated because its backing data could no longer be found in the store". So on that screen rows render from `DeletedItem` value snapshots and `@State` holds a `PersistentIdentifier`, never a model — `ModelContext.model(for:)` turns it back into an object at the one moment one is needed. Apply the same rule to any future hard delete.
- One type per file *ideally*, but tightly-coupled private helper views/types are co-located with their feature file (matches the existing code).
- Keep views small; push logic into view models / testable value types (e.g. `AnalyticsReport`, `BudgetSchedule`) and services.
- Comment the *why*, not the obvious *what*. When you add a dependency or make a structural choice, say so and explain why.
- **Art assets (`OshRat/Assets.xcassets`).** The catalog sits inside the synchronized `OshRat/` group, so adding or moving art needs **no** pbxproj edit (unlike code — see the next bullet). Mascot and wardrobe art is filed by folder group:
  ```
  Mascots/<Character>/Poses/   400×520 bust crop — spot art for toasts, headers, onboarding
  Mascots/<Character>/Rig/     360×660 full body — the shared wardrobe canvas
  Accessories/{Hats,Glasses,Outfits,Pants,Shoes,Props,Backgrounds}/   wardrobe items, one folder per slot
  ```
  **The subfolder tells you which canvas to draw on** — that's the whole point of the split, because layers only register when they share a viewBox. `Glasses` is its own slot (drawn under the hat, so a brim can overlap the frames); `Props` is the plan's front *accessory* slot (a coin, a bag), named so it doesn't read as `Accessories/Accessories`.
  Asset names are `<character>-<crop>-<pose>`. Two characters so far:
  - **`Classic`** — the suited, hatted rat in today's screens. Grandfathered names: `rat-mascot-*` (bust), `rat-fullbody-*` and the articulated `rat-part-*` (the Analytics rig) on the 360×660 canvas.
  - **`Bare`** — the hatless, suitless body the wardrobe dresses, as rig parts: `bare-bust-rig-*` (in `Poses/`) and `bare-fullbody-rig-*` (in `Rig/`). See *Wardrobe & avatar*.

  A new character or style is a new folder beside them with its own prefix.
  **Every SVG's nominal `width`/`height` is its canvas ÷ 4** (90×165 / 100×130, viewBox unchanged), and it carries no `<metadata>`: actool pre-renders each SVG at nominal size ×3 beside the vector, and full-canvas layers at full size were ~7.6 MB of an 8.6 MB `Assets.car`. Every art `Image` is `.resizable()`, so drawing still comes from the vector — keep it that way. `Scripts/import_avatar_pack.py` slims what it imports; `--slim-catalog` re-applies it to art added by hand.
  **Every Bare part and every wardrobe layer keeps the whole canvas**, so they register without offsets and a limb's layers rotate about the same pivot as the limb. Anything that rides a limb (sleeve, pant leg, shoe) must be cut for that limb at rest; the rig does the rest.
  **None of these folders provide a namespace**, deliberately: asset names stay flat, so `Image("rat-mascot-coin")` keeps working no matter which folder the file sits in, and the asset name stays usable as the catalog key. The cost is that **names must be unique across the whole catalog** — prefix per character, `item-<slot>-<name>` for wardrobe items. Moving art between folders is therefore free; verify a move with `xcrun assetutil --info <built>.app/Assets.car` rather than a build alone, which passes either way.
  **Rarity is a field in the code catalog, not a folder.** Rarity is a balancing decision that gets re-tuned; folders are for the slot, which never changes. (Per GAMIFICATION.md the item catalog lives in code, not the database.)
- **Where sources live:** `Models/`, `Views/`, `ViewModels/`, `Services/`, `DesignSystem/` sit at the **repo root**, not under `OshRat/` — that folder holds only the app entry, `Info.plist`, `Localizable.xcstrings`, sounds and assets.
- **Adding files (gotcha):** only the `OshRat/` folder is a synchronized Xcode group. New files under `Models/`, `Views/`, `ViewModels/`, `Services/`, `DesignSystem/` are **not** auto-detected — register each in `OshRat.xcodeproj/project.pbxproj` by hand (a `PBXBuildFile`, a `PBXFileReference`, an entry in the parent group's `children`, and an entry in the target's `PBXSourcesBuildPhase`). A file the **test targets** also need (anything `Account.swift` and friends reference) needs its own `PBXBuildFile` per target — three in total. **Object IDs must be unique across the whole file**: reusing one that already exists doesn't fail the lint, it silently rebinds the entry to the *other* file, and the new source is simply never compiled ("cannot find type X in scope" with no "Compiling X.swift" line). Validate with `plutil -lint OshRat.xcodeproj/project.pbxproj`, then confirm membership really resolved: `plutil -convert json -o /tmp/pb.json … ` and walk each target's sources phase from `fileRef` to `path`.
- **Build check:** `xcodebuild build -scheme OshRat -destination 'platform=iOS Simulator,name=iPhone 17 Pro'`.
- **A green test run can be stale.** `xcodebuild test` has been seen to reuse an `OshRatTests.xctest` built *before* a test file was edited — "TEST SUCCEEDED" with the new `@Test`s never run, and the console's "Test case … passed" lines don't list every Swift Testing result either. When a change adds tests, confirm they ran: pass `-resultBundlePath`, then `xcrun xcresulttool get test-results tests --path <bundle>` and look for the new names; if they're missing, `xcodebuild clean test`.
- **Tests are `@MainActor` structs:** a default argument can't call one of their static helpers (`now: Date = date(2027, 1, 1)` fails with "main actor-isolated … in a nonisolated context") — take an optional and resolve it inside instead.
- **Paged `ScrollView` gotcha:** every mounted page's body runs on each render, so per-page work multiplies by the page count — `HomeView.report(for:)` rebuilds a `BudgetVsActual` from the entire ledger, and `.defaultScrollAnchor(.center)` measures the whole row, which defeats `LazyHStack` — so the row is a plain `HStack` (a lazy one sized itself from the pages built so far and clipped the tallest card's bottom off). A ±240-period window meant ~481 ledger scans per render and a pinned main thread on a real device. Keep the window small and re-base it around the visible page instead of mounting a wide range.
- **`List` row-growth gotcha:** don't animate a `List` row's *height* to reveal content — insert a **separate row** instead. `List` is a UIKit collection view: a row that grows has its cell frame animated from its centre while SwiftUI has already laid the content out at the final size, so the content is misplaced mid-animation. Recorded frame by frame on the transactions list: the tapped row vanished for three frames and slid back in on opening, and drew over its neighbour on closing — and no SwiftUI-side fix inside the row (a fade instead of a slide, `.clipped()`, top-pinned content) changed that. Row insertion and removal are the collection view's own animations and are smooth. Also avoid a bouncy spring on list motion; an overshoot reads as the list wobbling.
- **Previewing a drawn shape without a build:** `qlmanage -t -s 1400 -o <dir> file.svg` rasterises an SVG, so a candidate `Shape` can be authored as SVG path data and eyeballed in seconds instead of a build/install/screenshot cycle each guess. Lay the candidates out in one sheet **and repeat them at icon size** (`transform="... scale(0.25)"`) — `RatHeadShape` looked fine large while its tail aliased to a wisp at 25pt, which only the small row showed. Note SVG fills each `<path>` separately whereas a SwiftUI `Shape` fills one `Path` of subpaths, so the preview will not reveal a winding conflict; check that by signed area.
- **Checking SF Symbol names without a build:** a throwaway Swift script — `import AppKit`, then `NSImage(systemSymbolName: name, accessibilityDescription: nil) == nil` per name — lists any that don't exist. Worth running whenever a list of symbol names is added.
- **Verifying UI on the simulator is limited:** `simctl` boot/install/launch/screenshot work, but AppleScript automation is blocked, so gestures can't be driven. A clean build is not evidence that a gesture or scroll change behaves — say so, and test interaction on a device. What *can* be driven is the starting state: `xcrun simctl launch booted com.oshrat.app.dev -demoScenario saver -demoTab analytics` fills the store and opens on a given tab (see the demo-data bullet above), so a data-driven screen can be screenshotted without tapping through onboarding first. `-demoEquip <item-id>` and `-demoWardrobe` do the same for the avatar and the wardrobe. Install the app from `BUILT_PRODUCTS_DIR` (`xcodebuild -scheme OshRat -configuration Debug … -showBuildSettings | grep " BUILT_PRODUCTS_DIR"`) — **always pass `-configuration Debug` to both the build and the lookup**: without it the lookup can resolve to `Release-iphonesimulator` while `build` writes `Debug-iphonesimulator`, and you install a stale release app (`com.oshrat.app`) and launch an old dev build (`com.oshrat.app.dev`) that has none of your changes, not whichever `DerivedData/OshRat-*` folder a `find` hits first — a stale one can hold an old template build that looks exactly like the simulator being stuck (the real app's UI is Hebrew; English means the wrong build). **Animations can be verified** even though they can't be triggered by touch: a temporary `// TMP-…` hook calls the real action on a timer (e.g. `toggleExpand` after 4 s), `xcrun simctl io booted recordVideo --codec=h264 out.mov` records it, and a few lines of Swift with `AVAssetImageGenerator` (zero tolerance, ~30 fps steps) tile the frames into a contact sheet. That is how the list's expansion glitch was seen, diagnosed and confirmed fixed; strip the hook afterwards. To screenshot something below the fold (a roadmap station, the end of a card), a temporary `// TMP-screenshot` hook either renders that view first in its `VStack` or adds `.defaultScrollAnchor(.bottom)` to the `ScrollView`. `grep -rn TMP Views` before committing. If `simctl` says "No devices are booted", run `xcrun simctl boot "iPhone 17 Pro"` and `xcrun simctl bootstatus "iPhone 17 Pro" -b` before installing.
