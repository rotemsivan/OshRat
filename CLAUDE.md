# עכבר עו״ש (OshRat)

> If you named the Xcode project something other than `OshRat`, update the name in this file to match it.

## What this app is

A personal finance app, in Hebrew, that helps one person track their money and feel in control of their financial state. There is intentionally **no connection to banks or investment providers** — the user enters and updates all balances and transactions manually. This is both a privacy choice and a simplicity choice.

This is also a **learning project**: the developer is new to iOS development. Prefer clear, idiomatic, well-commented Swift, and briefly explain non-obvious decisions as you go rather than only producing code.

## Names

- Project / module name (code, ASCII): `OshRat`
- Display name (what users see, Hebrew): עכבר עו״ש
- Theme (for a later design phase): rat / mouse themed. No design work yet.

## Platform & stack

- iOS only. Deployment target: **iOS 26** (project setting is 26.5). Uses SwiftData plus iOS 26 Liquid Glass APIs (e.g. `glassEffect` in `HomeBottomBar`).
- UI: SwiftUI.
- Persistence: SwiftData, local and on-device. No backend, no server, no network calls in the MVP — with **one explicit exception**: see *FX rates* below.
- Architecture: MVVM — SwiftUI views → view models → services → SwiftData models.
- Charts: Swift Charts (Apple's native framework).
- Language & layout: Hebrew, right-to-left. The app is **pinned to Hebrew on every device** (`CFBundleLocalizations = [he]` in `OshRat/Info.plist`, `developmentRegion = he`), so it always renders RTL regardless of the simulator/device system language. User-facing Hebrew is currently written inline as `Text("…")` literals; Swift treats these as `LocalizedStringKey`s and Xcode auto-extracts them into `OshRat/Localizable.xcstrings` (whose `sourceLanguage` is `he`, so the key *is* the final text — nothing to "translate"). Let SwiftUI mirror RTL automatically; for a `+`/`-` sign on an amount, wrap it in U+2066…U+2069 so the bidi-neutral sign stays on the visual left (see the summary cards).
- **Goal — finish the String Catalog migration:** make `Localizable.xcstrings` the source of truth for user-facing text, chiefly to get correct Hebrew **plurals** (1 / 2 / many differ, e.g. `%lld תנועות`) and to disambiguate / positionally reorder interpolated args. Migrating is safe and does **not** change the app's language: keys stay Hebrew and `CFBundleLocalizations = [he]` keeps it Hebrew + RTL. Do **not** add a second language (e.g. `en`) to the catalog or bundle localizations unless the app is genuinely going multilingual — that would let a non-Hebrew device flip the layout to LTR.
- Multi-currency: every account, holding, transaction, budget item, and goal carries its own ISO currency code (e.g. `ILS`, `USD`). The dashboard rolls everything into the user's **preferred currency** via cached FX rates (see below), falling back to per-currency / "FX unavailable" when rates are missing. Conversion goes through `CurrencyConverter`.

## FX rates (network exception)

The app pulls daily reference exchange rates from **Frankfurter.dev** (`https://api.frankfurter.dev/v1/latest`) so the dashboard can roll multi-currency totals into the user's preferred currency. This is the *only* network call the MVP makes.

Rules of the exception:
- **Public reference data only.** Frankfurter publishes ECB rates. No auth, no API key, no user identifiers in the request.
- **Cached aggressively.** Rates are stored in a `FXRateSnapshot` SwiftData row and refreshed at most once per 24h.
- **Graceful fallback.** If the fetch fails (or the cache is empty), the dashboard falls back to per-currency totals with a small "FX unavailable" note. Nothing in the rest of the app depends on a successful fetch.
- **Don't expand this exception** without updating this section. Anything that sends user data over the network — bank, brokerage, market-data, analytics, telemetry — needs a separate, deliberate decision.

## Money & data rules

- All monetary amounts use `Decimal`, never `Double` or `Float` (avoids rounding errors).
- Account balances are entered and updated **manually by the user** and are the source of truth for net worth. Transactions are a separate income/expense log that feeds the dashboard and budget — we do **not** auto-recompute balances from transactions in the MVP.
- Keep the data models **CloudKit-compatible** even though sync is off for now: every stored property must be optional or have a default value, and do not use unique constraints. This keeps the door open to enable iCloud sync later with almost no rework.

## Data models (SwiftData `@Model` classes)

Define these in a `Models/` group.

Shared enums (String-backed, `Codable`), all in `Models/SharedEnums.swift`:
- `TransactionKind`: `income`, `expense`
- `AccountType`: `current`, `digitalWallet`, `savings`, `investment`. Also carries the per-type `symbolName` (SF Symbol), `sortRank` (dashboard / analytics ordering) and `isLiquid` (the dashboard's נזיל / נכסים split) — use those rather than re-writing the switch in a view. Decodes unknown raw values to `.current`, so a removed case can't brick the whole store (as `.other` once did). **`.investment` is currently blocked in the UI** (see *Investments* below) but still a valid stored value.
- `DepositKind`: `oneTime`, `replenishable` — whether a deposit takes money once or keeps taking it (see *Deposits* below). Stored on `Account` as **`depositKindRaw` (a `String`) with a computed typed view**, the same shape `BudgetItem` uses: a Codable enum attribute added to a model that already has rows in the store traps on read (`swift_dynamicCast` failure inside SwiftData), where a defaulted `String` migrates silently. Decodes unknown raw values to `.oneTime`.
- `CategoryNature`: `need`, `want`, `neutral` (powers needs-vs-wants)
- `RecurrenceUnit`: `day`, `week`, `month`, `year` — the current cadence model ("every N units"). Sub-monthly units average into *every* month; monthly/yearly land their full amount on the months they occur in.
- `BudgetFrequencyKind` / `BudgetScheduleKind` — **legacy**, superseded by `RecurrenceUnit` + a count. Still persisted so pre-existing `BudgetItem` rows migrate cleanly, and `BudgetScheduleKind` still distinguishes `oneTime` from recurring.

Models:
- **UserProfile** — name, profession, free-text goals, preferred currency code, createdAt. Holds the personal data from onboarding.
- **Account** — name, type (`AccountType`), balance (`Decimal`), currency code, lastUpdated, isFavorite; relationships to its transactions (nullify) and holdings (cascade). The manually managed balances. A `.savings` account is a **deposit (פיקדון)**: it also carries `interestRatePercent`, `depositStartDate`, `maturityDate`, `autoPayoutOnMaturity`, `payoutAccount` (a self-referencing nullify relationship, inverse `incomingDepositPayouts`) and `payoutCompletedAt`. All optional/defaulted, all ignored unless the type is `.savings`, and all-empty is a valid open-ended savings pot. `depositTerms` bridges them to `DepositTerms` and `depositLadder` to `DepositLadder` (**read the ladder** — it answers the same questions for both deposit kinds); `isAwaitingPayout(asOf:)`, which the dashboard prompt *and* the "ממתין לפדיון" badge key on, is ladder-based, so a replenishable deposit only comes due once its **last** sub-deposit has. `depositKind` + a cascade `depositTranches` relationship carry the replenishable case; `effectiveMaturityDate`, `openingDepositAmount` and `depositCount` are the derived reads the views use. **A deposit never carries the favourite star** — `AccountType.allowsFavorite` is false for `.savings`, because favourite means *the default account for a new transaction* and a deposit is money you can't spend. Enforced at every write point (`AccountDraft.apply`, `OnboardingViewModel.commit`, `HomeView.onToggleFavorite`) rather than defended per view; `clearFavoriteIfNotAllowed()` heals rows starred before the rule existed, called once from `HomeView`.
- **Holding** — symbol, name, quantity, marketValue (`Decimal`), currency code, lastUpdated; belongs to an investment `Account`. A single manually-valued position (stock/ETF).
- **Category** — name (Hebrew label), kind (`TransactionKind`), nature (`CategoryNature`), colorHex, SF Symbol name; relationship to its transactions.
- **Transaction** — amount (`Decimal`), kind, date, title, note, currency code, optional balanceAfter; optional links to a Category and an Account, plus a cascade `attachments` relationship. The income/expense log. A row logged from a scheduled budget line also carries `budgetItem` (nullify) and `budgetOccurrenceDate` — *which* scheduled day it settles, kept apart from `date` (when the money moved, today by default) so logging next week's rent early greys next week, not today. (A "manual balance edit" marker title flags bookkeeping rows so totals can exclude them.)
- **TransactionAttachment** — filename, `@Attribute(.externalStorage)` data blob, typeIdentifier (UTI string), createdAt; belongs to a `Transaction` (cascade). A receipt/invoice the user attached — image or PDF — added from Camera/Photos/Files in the transaction sheet and viewed (via QuickLook) from the expandable transaction card. Camera needs `NSCameraUsageDescription` in `OshRat/Info.plist`.
- **BudgetItem** — optional Category, plannedAmount (`Decimal`), kind, currency code, frequency (`BudgetFrequencyKind`), and an optional **schedule** (`BudgetScheduleKind` + day/month/year, plus an optional month/year **end bound** for recurring lines — "until January 2028"). `plannedAmount(inMonth:year:)` attributes each line to the right month; `occurrenceDate(...)` resolves the calendar day and, for **income**, shifts it off Shabbat *and Israeli holidays* to the next business day by default via `businessDay(onOrAfter:)` + `IsraeliHolidays`. Feeds planned-vs-actual and the budget calendar (which tints Shabbat and holidays). `lastEditedAt` is stamped by `init` and, through the drafts' `apply(to:)`, only when `editableFields` actually changed — the budget achievements key on it (deletions go to `UserProgress.budgetLastTouchedAt`). Also carries the inverse `loggedTransactions` and the two budget-reminder stamps, `reminderAnnouncedFor` / `reminderAcknowledgedFor` (start of day; see *Budget reminders*) — both deliberately **outside** `editableFields`, since seeing a reminder isn't editing the budget. `displayTitle` is the line's one-line name (income: source; expense: category — note), shared by the calendar rows and the toast.
- **DepositTranche** — one sub-deposit ("הפקדה") inside a *replenishable* deposit: amount, its own `interestRatePercent` and `maturityDate`, startDate, note, its `account` (cascade) and the `fundingTransaction` that created it (cascade from `Transaction.fundedDepositTranches`). Rates and dates are **copied** from the account at creation, not inherited by reference — terms agreed in March shouldn't change because the account's defaults were edited in June. `isLive` is false while the funding transfer sits in Recently Deleted, which is how a deleted transfer drops its rung out of the ladder and a restore brings it back. The **opening** deposit has no row: it's derived as the remainder (see `DepositLadder`).
- **Goal** — title, targetAmount, savedAmount (`Decimal`), optional targetDate, note, currency code, isCompleted, optional `createdAt` / `completedAt` (the Goals UI must set `completedAt`; `goal-done` needs both). Covers goals and future plans.
- **FXRateSnapshot** — base currency, rates map, fetchedAt. Cached daily exchange rates (see *FX rates* above).
- **UserProgress** — the one XP row: totalXP, currentStreak/longestStreak/lastActivityDate, `awardedKeys` (one-time awards already paid), the daily-cap counter and its date, `pendingCelebrations` (the toast queue, as `Celebration` raw values — `level:N`, `achievement:<id>`, `achievements:N`; `pendingLevelUpLevel` is its legacy predecessor, moved into the queue on first read), the last-award marker, and the achievements state: `unlockedAchievements` (ids, the patch ledger), `achievementsEpoch`, `budgetLastTouchedAt`. Only *progress* is stored — what earns XP and what a level costs are code constants in `XPRules`, so rebalancing is an edit, not a migration. See *Gamification* below.
- **MascotConfig** — what the user's rat wears: one optional equipped item id per wardrobe slot (`backgroundID`, `outfitID`, `hatID`, `propID`), all `nil` for the Bare rat everyone starts as. One row, resolved oldest-first by `WardrobeService.config(in:)`. Unlocks are *not* stored — they derive from the level.

Not a `@Model`, but part of the same layer:
- **XPRules** (`Models/XPRules.swift`) — the single tunable config (XP amounts, the daily cap, streak milestones, the level curve) plus the pure maths: `level(forTotalXP:)`, `totalXP(toReach:)`, `progress(forTotalXP:)` → `LevelProgress`, `nextStreak(...)`, `cappedAward(...)`. Also holds `XPReason`, whose raw values are persisted — add cases, never rename them. Unit-tested (`OshRatTests/XPRulesTests.swift`) and compiled into the test targets — see the pbxproj gotcha below.
- **Achievement** / **AchievementEvaluator** (`Models/`) — the 24-entry catalogue as code (`id` is persisted — never rename) and the pure rules: an `AchievementSnapshot` of plain values in, satisfied ids out. `ProgressService` builds the snapshot; month money verdicts come from `BudgetVsActual`, never reimplemented. Tested in `OshRatTests/AchievementEvaluatorTests.swift`; both files are in the test targets.
- **WardrobeItem** (`Models/WardrobeItem.swift`) — the wardrobe catalogue as code: id (persisted in `MascotConfig` *and* the asset-name stem, so never rename), Hebrew name, `WardrobeSlot`, tier (the achievement metals) and `unlockLevel`. Adding an item is one catalogue line plus its two SVGs. Tested in `OshRatTests/WardrobeCatalogTests.swift`; in the test targets.
- **DepositTerms** (`Models/DepositTerms.swift`) — the pure, unit-tested term maths behind a deposit: `isMatured`, `daysRemaining`, `progress`, `value(asOf:)`, `projectedValue`. **Simple annual interest** (`principal × (1 + rate × years)`, 365-day years), not compounding: the user can reproduce it on a calculator, and the payout prompt lets them overwrite it with the bank's real figure anyway. Accrual stops at maturity. Compiled into the test targets as well as the app — see the pbxproj gotcha below.
- **DepositLadder** (`Models/DepositLadder.swift`) — the pure, unit-tested sum of a deposit's sub-deposits: total principal, `value(asOf:)`, `projectedValue`, and a `maturityDate` that is the **latest** rung's (nil while any rung is open-ended, so a deposit still taking money never prompts). A one-time deposit is a one-rung ladder, so every screen reads the ladder and stops caring which kind it is. `make(balance:opening:additions:)` reconciles the rungs against the account balance: the **opening deposit is the plug** (`balance − Σ additions`, never stored, so it can't drift from the balance a hand-correction or a deleted transfer just moved), and when the additions exceed the balance the shortfall comes off the **newest** end. Also in the test targets.
- **CategoryBudgetStatus** (in `Models/BudgetItem.swift`, so the test target already compiles it; tested in `OshRatTests/CategoryBudgetStatusTests.swift`) — one category's month, planned vs actual, for the bar in a transaction's expanded card. Counted by `BudgetVsActual`'s rules, narrowed to a category: every budget line of it adds `plannedAmount(inMonth:year:)`, every real row of it in the month adds its amount (transfers and manual balance edits out), both in the preferred currency with unconvertible rows skipped and flagged. `nil` when nothing is planned. `make` expects the ledger **newest first** and stops at the first row before the month, so opening a recent transaction reads a month of rows rather than the whole history — it runs on the card's opening frame. Months are Gregorian, as `BudgetItem`'s are.

Register all models in the app's `.modelContainer(for: [...])` at launch (`OshRatApp`).

## Features (build order)

MVP, roughly in this order (1–3 implemented; 4 not yet):
1. **Onboarding / setup wizard** — collect personal data → financial accounts (current, investment) → budget (planned income & expenses). **The budget step is optional, income included** — the app is about managing spending and not everyone has a fixed income to plan. `OnboardingViewModel.canContinue` is always true there, and the last button reads "דילוג וסיום" while both lists are empty (`isBudgetEmpty`). Everything downstream copes with no plan: the dashboard card falls back to actuals only (its empty state points at the pencil), a bucket with nothing planned shows no percentage, and the overrun alert needs a non-zero expense plan. Keep it that way — don't reintroduce a required budget line. Seed a default set of Hebrew income/expense categories on first launch.
2. **Dashboard** — a clean, minimal, friendly summary: net worth, this month's income vs expenses, budget progress (month-aware), goal progress. The assets card splits its rows into **נזיל** (עו״ש + ארנק דיגיטלי) and **נכסים** (פיקדונות + השקעות) by `AccountType.isLiquid`, each with its own subtotal under the combined total. Rows are **capped at the first three** (a "הצג עוד" toggle at the card's bottom-left opens the rest) so the card can't push the budget card off-screen; collapsing hides *rows only* — each group header still subtotals every account in it, so the parts keep adding up to the hero total.
3. **Transactions** — add / edit / delete income and expenses (and transfers) anytime, each with a category and account. **Multi-select**: long-press a row to enter selection mode, tap to add rows, "בחירת הכל" takes everything the current filters leave on screen (not the whole store), and the bar's trash soft-deletes the batch behind one confirmation. Selection mode collapses any open insights card and disables the row swipes, so a tap means one thing at a time. **Copy**: the row's *leading* swipe (visual right, swiping left; full swipe fires it) opens `NewTransactionSheet(copying:)` titled "העתקת תנועה" — kind, accounts, category, title, note, amount and currency carry over (transfers copy as transfers), but the **date is today**, and **attachments** and the **budget-occurrence link** are deliberately left behind (a receipt belongs to its purchase; a second link would count the occurrence twice). A soft-deleted account isn't copied — `primeDefaults` re-picks it, and a transfer re-picks a missing destination — and the amount keeps its currency even when the account is re-picked (the same `old == nil` guard the budget link uses). Manual balance edits have no copy swipe. **Filters live in `TransactionFilters`** (`ViewModels/`), owned by `HomeView` — `HomeView` rebuilds each tab branch on switch, so filters held in the list's own `@State` were wiped by a glance at the dashboard. Session-scoped, deliberately not `@AppStorage`: a filter set last week that silently hides most of the ledger on a cold launch is a bug report waiting to happen. The rest of the list's design is in the bullets below.
   - **Filters & sort** (`TransactionFilters`, tested in `OshRatTests/TransactionFiltersTests.swift`). Each active filter is its own removable chip in `ActiveFiltersBar` under the search field — type, category, dates — plus "ניקוי הכל" once two or more are on; a single "reset everything" chip used to throw away a carefully picked category along with a date range. Chips appear without animation on purpose: the same change reshapes the list, and an animated diff of a page of rows hitches. The sheet's dates are a one-tap `DatePresetGrid` (adaptive columns on a `@ScaledMetric` width, so large text drops columns rather than truncating) of **calendar** presets (החודש / החודש שעבר / השנה — how a budget is read) and **rolling** ones (7 / 30 / 90 days), with the resolved days captioned (`rangeDescription`); "טווח מותאם" is `beginCustomRange()`, which seeds both pickers from the window already showing and caps the end at today. Every window is **whole days, half-open** (`start <= date < end`) — a rolling window cut at the current time of day left the oldest day's group half-empty — and cut in a **Gregorian** calendar, since a device set to the Hebrew calendar would otherwise make "this month" a Hebrew month. The sheet opens at a `.fraction(0.7)` detent: `.medium` cut the date grid off, and 0.7 keeps the chips visible above it so each tap shows up live. **Sort** (`TransactionSort`) is a toolbar `Menu` beside the filter button, sharing its glass group. It is *not* a filter: it's outside `hasActiveFilters` and survives `clear()`. It runs once per render, after filtering; the date orders are free (as delivered, or reversed), and the amount orders rank in the preferred currency (`rankingAmount()`, one FX factor per currency — `FXRateSnapshot.rates` re-decodes JSON on every access) on a `(Double, index)` key, which took a 20,000-row ranking from ~140 ms to ~34 ms. Amount orders drop the day headers (every row would get one) and rows show their own date instead. Because sorted order isn't date order, a similar-transaction jump to a row the filters hide can't read its position off `allTransactions`: it sets `pendingJumpID`, clears the filters, and finishes in `onChange(of: resetKey)` against the real rows.
   - **Expanded card** (`ExpandedTransactionCard`). The card is **its own `List` row**, inserted after the transaction's (`row(_:proxy:)` is a `@ViewBuilder` yielding two rows) — never extra height on the tapped row. See the `List` row-growth gotcha in Conventions for why; the tapped row now never moves, and the whole motion shares one bounce-free timing (`ExpansionMotion.animation`). It leads with the category's budget for the **transaction's own month** — `CategoryBudgetStatus` drawn with the dashboard's `BudgetProgressBar`: blue with room left, orange from 90%, red with "חריגה של" once over, green for income; no bar when nothing is planned. Then the note, insights (`TransactionInsights`), attachments — gated on the list's `attachedIDs` rather than `transaction.attachments`, which faults the rows in on the opening frame — and similar transactions: up to 10, three visible, scrolling inside the block. That box is sized by laying out the first three rows `.hidden()` and overlaying the `ScrollView` on exactly that space; measuring rows into state would resize the card a frame after it appears.
   - **Search** (`ViewModels/HebrewSearch.swift`, `ViewModels/TransactionSearchIndex.swift`, tested in `OshRatTests/TransactionSearchTests.swift`; both files are in the test target alongside `TransactionFilters`). Covers title, note, category, **account names** and the **amount** (plain digits, so "120" finds ₪120.50). `HebrewSearch.fold` is the one canonical form for query and haystack: lowercased, niqqud dropped, **final letters folded** (ן→נ…), geresh/gershayim and quotes removed, other punctuation → space. Every query word must match somewhere (AND), and each match is tiered by `SearchMatchTier`:
     - **exact** — the folded text contains the token;
     - **spelling** — the vowel-less *skeleton* matches (ו/י dropped after the first letter: תוכנית ↔ תכנית);
     - **typo** — within a weighted edit distance of a word or its prefix (so a half-typed word already matches). Budget by length: ≤2 letters exact only, 3 → 0.5, 4–6 → 1, 7+ → 2; a substitution between **neighbouring keys on the Hebrew keyboard costs 0.5** (so "יקקן" finds "ירקן" — ק sits beside ר). Numeric tokens are never typo-matched.
     A query with Latin letters is also tried as if typed on the **Hebrew layout** ("hrei" → ירקן). `TransactionFilters.results` returns typo matches **only when nothing matched exactly or by spelling**, with `isApproximate` set so the list says "לא נמצאה התאמה מדויקת — מוצגות תוצאות דומות" — mixing them in would bury the real hit under every word one letter away. `TransactionSearchIndex` caches each row's folded words and rebuilds an entry only when its raw source strings differ, so edits and renamed accounts need no invalidation; it lives `@ObservationIgnored` on `TransactionFilters` (a cache filled during render mustn't schedule another render) and prunes orphans once they outnumber live rows. The view applies the search through a ~180 ms debounce (`appliedSearch`, a `task(id: filters.search)`); clearing applies at once.
   - **List performance** (`Views/Transactions/TransactionsListView.swift`) — it was glitchy on a long ledger, and each of these fixed a measured cost:
     - **Filter once per render.** `body` computes `filters.results(...)` into a `let` and passes it down. It used to be a computed property read from three places, so every render filtered the ledger several times over.
     - **The parent/child split.** `TransactionsListView` owns the query, the search field and the filter pass; the private `TransactionLedger` owns everything that changes while browsing — expanded row, jump highlight, multi-select, the page size. State that changes on a tap must live in the child, or the tap re-runs the whole filter pipeline.
     - **Paging.** The ledger mounts `pageSize` (120) rows; a `ProgressView` footer, re-identified by `.id(rowLimit)` so it fires again if still on screen, mounts the next page. `List` builds row *views* lazily but re-diffs every row *identity* on every update. Reset on any `LedgerQueryKey` change. "בחירת הכל" still selects every matching row, mounted or not, and a similar-transaction jump raises the limit to reach its target first.
     - **No per-row faults.** The `@Query` is a `FetchDescriptor` with `relationshipKeyPathsForPrefetching` for category/account/destination, and the paperclip comes from one `TransactionAttachment` query (`propertiesToFetch = [\.transaction]`) turned into a set of ids. Reading `transaction.attachments` in a row fires a to-many fault per row as it scrolls — including small blobs stored inline — so don't bring it back.
     - Day groups are built in one linear pass: under a date order the rows arrive date-sorted (as queried, or reversed), so there's no dictionary to build and nothing to re-sort. An amount order renders one headerless group.
4. **Goals & future plans** — create and track savings goals. *(model exists; UI not built yet.)*

**Investments — deliberately off.** `.investment` stays in the account-type picker (it's coming) but selecting it bounces back, with a "בפיתוח" note explaining why; a segmented `Picker` can't disable one segment, so the revert *is* the affordance. Accounts that are *already* investments still open and edit normally — `AccountEditorSheet.originalType` is what permits that. In the meantime securities are logged as ordinary transactions through two seeded categories, **קניית ני״ע** (expense) and **מכירת ני״ע** (income). Both are `.neutral`, which today means a purchase counts under **צרכים** in needs-vs-wants and the budget card — a known distortion, accepted until investment accounts are real.

Also built since:
- **Deposits** (`Models/DepositTerms.swift`, `Models/DepositLadder.swift`, `Models/DepositTranche.swift`, `Services/DepositPayoutService.swift`, `Services/DepositLadderService.swift`, `Views/Home/DepositMaturitySheet.swift`) — a savings account with a rate, a start date, a maturity date, a payout account and an auto/ask toggle. **Two kinds**, picked with the "אפשר הפקדות נוספות" toggle at the top of the editor's deposit section: a **one-time** deposit (money in once, term runs, pays out) and a **replenishable** one the user keeps adding to. In the replenishable case *every transfer that credits the account becomes a sub-deposit of its own* — `DepositLadderService.registerFunding` writes the rung off the transfer in `NewTransactionSheet.insertTransfer`, copying the account's rate and **term length** (so "a one-year deposit" still means a year for money added six months in). The account's own rate/start/maturity are then the **defaults** new rungs inherit, the labels on the editor say so, and the whole deposit pays out on the **latest** rung's maturity. Neither kind compounds — each rung earns simple interest on its own principal, and compounding is rare enough to be a later addition. `DepositInfoSheet` lists the rungs ("ההפקדות בפיקדון", opening deposit first) and each one opens a small editor for its rate and maturity, since the bank sometimes quotes a different figure for a particular deposit. Toggling replenishable *off* makes the ladder ignore the rungs (one deposit again) without deleting them, so toggling back on restores them intact. **Payout targets are `.current` accounts only** (`HomeView.payoutCandidates`) — a deposit matures into an עו״ש, not into another deposit or a wallet; the one exception is an account a deposit already points at, kept in the list so older data doesn't silently lose its target. On the maturity day `HomeView` settles it: deposits set to automatic (and with a live payout account it can reach) transfer on their own and raise a one-button confirmation; the rest raise `DepositMaturitySheet`, which pre-fills the projected value, lets the user correct it and pick a different target, and offers "לא עכשיו" (session-scoped — it asks again next launch). **The payout writes two rows**: the interest as income on the deposit (without it, transferring principal+interest would drag the deposit negative) and the move itself as a normal transfer, so it reverses and restores like any other row. `payoutCompletedAt` latches it closed; the account stays at zero with its terms intact. A deposit sitting past its maturity date with the money still in it shows a **"ממתין לפדיון" badge** on its assets-card row (and drops the now-duplicate "הגיע לפדיון" from the row subtitle). The badge is deliberately *not* conditioned on `autoPayoutOnMaturity`: an automatic deposit is settled by `settleMaturedDeposits` the moment the dashboard appears, so it isn't in that state anyway — and one that *does* linger (payout account deleted, or no FX rate to bridge two currencies) needs attention more, not less. The little **"i"** beside a deposit row opens `DepositInfoSheet` — a read-only fact sheet (terms, accrued interest, projection, target, status, a term progress bar) plus the deposit's **history**, built by `DepositHistoryEntry.entries(for:)` from both sides it can appear on (`transactions` as source, `incomingTransfers` as destination). History amounts are signed *from the deposit's point of view*, unlike the global transactions list which shows transfers unsigned — here the frame is one account, so a payout that emptied it has to read negative. **Tapping the badge opens the maturity prompt** (and lifts the deposit out of `postponedDeposits` — reaching for the badge *is* taking it off "later"), so the reminder and the way to act on it are one control; this is the way back in after a "לא עכשיו", which is otherwise session-scoped and silent until the next launch. That badge is why the assets-card row's primary tap is a **`.contentShape` + `.onTapGesture`, not a `Button`**: the row carries three taps (edit, pay out, info), and a button nested in another button's label fires both, while a button inside a plain view with its own tap gesture does not — the button claims its bounds and the gesture takes the rest. Keeping the row a `Button` would have forced the badge out to the trailing edge just to stay tappable. The row therefore sets `.accessibilityAddTraits(.isButton)` by hand, since a tap gesture carries no button semantics. The info button stays a **sibling** of the row for the same nesting reason.
- **Profile** (`Views/Profile/ProfileView.swift`) — the fifth tab, behind the rat at the bar's right edge. In the order the questions get asked: a **card-less identity header** — avatar, name and profession reading across one compact row (RTL puts the picture on the right, like the dashboard's greeting mascot) — then a **stats** card (joined month/year from `UserProfile.createdAt`, current streak), the free-text goal from onboarding, then `LevelProgressCard`, then the **achievements shelf** (`Views/Gamification/AchievementsShelf.swift`): every catalogue patch grouped by theme in an adaptive `LazyVGrid`, earned ones struck in their tier's metal (`Theme.Colors.tier*`), locked ones dashed but *named*, each opening a popover with `Achievement.hint`. Catalogue order, not earned-first, so patches don't move as they unlock. Three layout notes: the stats `Divider` needs an explicit height or it collapses inside its `HStack`; the header carries no card **on purpose**, because a centred portrait in its own panel above a second panel for the name ate most of the first screen; and `ProfileAvatar` takes a `diameter` (68 here) — its `@ScaledMetric` must be declared **bare**, since spelling `relativeTo:` in the attribute *and* assigning the wrapper in `init` leaves it demanding a `wrappedValue` the caller cannot supply. `LevelProgressCard`'s top-trailing pill shows the **most recently earned achievement** (the last catalogue id in `unlockedAchievements`, which is kept in earning order), as a small `AchievementBadge` plus its title; before the first achievement it shows the streak instead, so a new card isn't missing a corner. The profile stats row is the streak's permanent home. **Read-only**: the personal details belong to the planned Settings screen. The two goal patches, which can't be earned until the Goals UI exists, say so in their popover rather than posing as ordinary locked ones. The avatar is the **user's own rat** (`UserAvatar`), and tapping it opens the wardrobe. Its circle crop lives in `AvatarPortrait` (`Views/Avatar/`), derived from the bust SVG's coordinates rather than nudged by eye: `.head` (zoom 1.75, centred on y 160 — the ears cap it near 1.77) for a bare rat, `.headroom` (zoom 1.35, centred on y 150) when a hat is on, because a propeller's blades (x≈130–270 at y≈56) fall outside the close circle.
- **Analytics** (`Views/Analytics/`) — a vertical, gamified "roadmap" of stats (monthly/yearly, month-over-month comparison, spending by category, needs-vs-wants, records, assets). All number-crunching is in the testable `AnalyticsReport`; stations reveal on scroll.
- **Budget scheduling & calendar** (`Views/Budget/`) — scheduled budget lines (every month / every year / one-time) that flow into the correct month automatically, plus a month `BudgetCalendarView` to plan them. The shared `BudgetScheduleSection` is reused by the income and expense editors. Adding a line goes through a `Menu` anchored to whichever button opened it (toolbar or the day card's "הוספת פריט ליום זה"), **not** a `confirmationDialog` — a dialog detaches from its source and surfaces away from the button that summoned it. The calendar card carries the visible month's planned income / expense / net as **one icon line** under the grid (`MonthPlanStrip`: ↙ / ↗ / =, whole shekels, stacking at large text sizes) — it used to be a card of its own, which pushed the day's items off-screen; and tapping a date **scrolls the day card into view** (`ScrollViewReader`, on change only, so landing on the tab keeps the grid in view). The day's rows are an embedded, scroll-disabled, fixed-height `List` (the `AssetsSummaryCard` pattern) purely for `.swipeActions`: **trailing** (visual left, swipe right, full swipe) deletes behind a confirmation — a budget line has no Recently Deleted and a recurring one takes every month with it; **leading** (visual right, swipe left) shows a wallet that opens `NewTransactionSheet(logging:occurrenceDay:)`. Deleting a line is a **hard delete**, so rows render from `CalendarDayEntry` value snapshots and act through `BudgetLogRequest` / an id looked up in the live `@Query` — the hard-delete trap in Conventions. An occurrence a live transaction already logs is drawn **grey** (row and grid dot) and loses the wallet, so it can't be counted twice; deleting that transaction un-greys it.
- **Budget reminders** (`Models/BudgetReminder.swift`, `Services/BudgetReminderService.swift`, `Views/Budget/BudgetReminderToast.swift`) — nudges the user to log what the budget says happens today. **Derived, not queued**: a line is *due* when `BudgetReminderService.occurrence(of:on:)` lands it on today and no live transaction logs that `BudgetOccurrence` (item id + day). Two stamps on `BudgetItem` decide how loudly to say so:
  - **Toast** (`reminderAnnouncedFor`) — `BudgetReminderToast`, the same card, slot and rhythm as `CelebrationToast`, overlaid by `HomeView` only when no celebration is pending and no modal is up, so the two never stack. It plays once per line per day, stamped when it finishes animating out (a cancelled run leaves it unstamped, so it replays). One line → a tap opens the new-transaction sheet pre-filled from it; more than `batchThreshold` (2) → one "N פריטים מתוכננים להיום" toast whose tap opens the calendar. Its payload is a `BudgetReminder` value snapshot, not the model, and `markAnnounced` takes models resolved from `HomeView`'s live `@Query` — `ModelContext.model(for:)` on a just-deleted line hands back an object that traps on write.
  - **Badge** (`reminderAcknowledgedFor`) — a small bell on the calendar tab icon (`HomeBottomBar.calendarHasReminder`) until the user opens the calendar, whose `.task(id: dueTodayIDs)` acknowledges today's due lines (which also counts as announced) and draws their rows with an accent wash and a bell ("להיום · החליקו לרישום"). Logging the occurrence clears everything, since it stops being due.
  - **Only today reminds.** An unlogged line from yesterday just stays un-greyed in the calendar — no catching-up nag, in the spirit of GAMIFICATION.md.
  - Occurrences are resolved in a **Gregorian** calendar (`BudgetReminderService.calendar`), since `BudgetItem`'s month/year numbers are Gregorian and a device set to the Hebrew calendar would misread them. `HomeView.today` is `@State`, refreshed by `UIApplication.significantTimeChangeNotification`, because nothing else re-renders at midnight.
  - The **pre-filled sheet** (`NewTransactionSheet.init(logging:occurrenceDay:)`) seeds kind, amount, currency, category and title from the line; the date stays today and is freely editable, and any line on any day can be logged this way. It prefers an account in the line's currency and must not let the first auto-picked account re-label the amount's currency (the `old == nil` guard in `onChange(of: sourceAccount)`). An income line with no category gets the same-named category if one exists.
- **Soft delete & recovery** (`Services/TrashService.swift`, `Views/RecentlyDeleted/`) — deleting an account or a transaction hides it rather than destroying it; `RecentlyDeletedView` restores or permanently deletes, and `HomeView` purges rows older than 30 days on appear.
- **Quick-add widget** (`OshRatWidget/`) — a static home-screen widget that deep-links `oshrat://new-transaction` straight into the new-transaction sheet.
- **Demo data & admin panel — DEBUG only** (`Services/DemoDataService.swift`, `Services/DemoScenarioBlueprints.swift`, `Views/Admin/AdminPanelView.swift`) — four ready-made lives (בתחילת הדרך / משפחה עם ילדים / חוסך עם פיקדונות / עצמאי), each generating months of real rows: accounts, budget lines mirroring the recurring spend, goals, a full ledger, a cached FX snapshot and an XP standing. Reached from the **hammer** beside the dashboard greeting *and* from the onboarding screen (a wipe drops the app back into the wizard, so the panel has to be reachable from there too), or from the command line: `-demoScenario <id> [-demoMonths N] [-demoTab analytics|transactions|calendar]`, and `-resetStore`. The whole thing is wrapped in `#if DEBUG` and is never compiled into a release build. Design rules worth keeping:
- **Deploying always wipes first.** A scenario is a whole life, not a top-up; merging one into leftover data gives balances that match nothing.
- **A wipe from a live UI must go through `prepareForDestructiveWork` first** — it deletes the `UserProfile`, which routes `ContentView` to onboarding, and waits for the dashboard to come down. Deleting accounts while the assets card is mounted traps in `Account.type.getter` from inside `ForEach`'s update (the hard-delete trap in Conventions, in its "backing data was detached" form). Only the launch-argument path may wipe directly, because no window exists yet. The panel dismisses itself before starting and does the work in an unstructured `Task`, which isn't cancelled when the sheet goes away.
- **The blueprint declares the *closing* balance, and the opening is back-solved** from the generated rows (`netDeltas`). Typing both independently is how a two-year history of salary quietly inflates the dashboard into six figures — which it did, until the ledger and the balance were made to agree by construction.
- **Wallets are topped up from the primary account** when they'd go overdrawn (`withWalletTopUps`), because every scenario charges coffee and deliveries to ביט and nothing ever refills it. Without this a wallet ends the history tens of thousands in the red.
- **Deterministic**: one fixed seed per scenario (SplitMix64), so redeploying reproduces the same ledger exactly and a bug found in demo data can be chased.
- Transfers into a replenishable deposit go through `DepositLadderService.registerFunding`, the same call the transfer sheet makes — so a demo ladder is built exactly like a real one (the family scenario produces ~22 sub-deposits, the saver ~30).
- **Gamification — XP core** (`Models/XPRules.swift`, `Models/UserProgress.swift`, `Services/ProgressService.swift`, `Views/Gamification/`) — **phase 1 of GAMIFICATION.md**, local-only. See *Gamification* below.
- **Wardrobe & avatar** (`Views/Wardrobe/`, `Views/Avatar/`, `Models/WardrobeItem.swift`, `Models/MascotConfig.swift`, `Services/WardrobeService.swift`) — phase 3 of GAMIFICATION.md. **Every appearance of "the user's rat" goes through `UserAvatar`**, which reads `MascotConfig` itself and stacks the layers back to front (background, Bare body, outfit, hat, prop) on one canvas — so the dashboard greeting, the profile picture and the celebration toasts all change the moment something is equipped. `AvatarLayers` is the same drawing from an explicit outfit (the wardrobe tiles preview items with it). Poses missing on a canvas fall back to `base` (`AvatarPose.bodyAssetName`). The wardrobe is a **full-screen cover** owned by `HomeView`, opened from the greeting rat, the profile picture, or a level-up toast that unlocked an item (it's in `isPresentingModal`, so toasts wait for it). It uses the system **zoom transition**: each rat is a `.matchedTransitionSource` keyed by `WardrobeEntryPoint` in `HomeView`'s namespace, so the screen grows out of whichever rat was tapped and a swipe down shrinks it back; the toast has no source rat. `matchedTransitionSource` only accepts a `RoundedRectangle` clip, so the round profile picture uses one with a corner radius of **exactly** half its diameter — an oversized radius is *not* clamped there and made the whole picture disappear. Reduce Motion gets the plain cover instead of the zoom. **The rat moves**, via `KeyframeAnimator`: the greeting rat rests in its base pose and waves briefly each time the dashboard appears (`onAppear` bumps a trigger — the branch is rebuilt on every switch to Home), and the wardrobe rat idles with a slow breath and sway anchored at its feet (one 4.8 s period for both tracks, so the loop has no seam). The art is one drawing per pose, so an arm can't swing by itself: the wave is the wave pose plus a whole-body tilt. Under Reduce Motion the tilt, hop and idle loop are off. The full-body canvas runs well below the feet (they rest at y 568 of 660), so the wardrobe trims that band out of the layout and centres the floor shadow on the feet from the same coordinate. Tapping an unlocked item equips and saves it at once; locked items show their level. `UserAvatar` also hides anything the current level hasn't unlocked, so a rebalance can't leave the rat wearing a locked item. **The Classic rat stays** in three places on purpose: the onboarding welcome (the brand, shown before an avatar exists), the account editor's favourite toggle (an icon, not "you") and the Analytics hopping rig (built from Classic parts — a Bare rig would let hats ride its head). DEBUG: `-demoEquip <item-id>` equips after any deploy, `-demoWardrobe` opens the sheet at launch.

Later (not now): networked gamification — streaks, competing with friends. This will need a backend and is out of scope for the MVP. (The Analytics page's gamification is purely local.)

## Gamification (XP core)

Phase 1 of `GAMIFICATION.md` is built, and so is phase 2's **engine** (per `ACHIEVEMENTS.md`) plus the profile shelf that draws the patches, and phase 3's wardrobe with a first set of eight level-unlocked hats; phase 4 (polish) is not. The full plan, including the layered-SVG mascot design, lives in that file — this section is just how the shipped part works.

- **`ProgressService` is the only thing that awards XP**, and it's called from the app's existing write points, never from a view's own logic: `NewTransactionSheet.handleConfirm` (new rows only — an edit is not new activity, or re-saving a row would farm points), `AccountDraft.apply` (on a real balance change) and `OnboardingViewModel.commit` (the setup milestones). Every entry point saves, so callers don't have to remember to.
- **All judgement lives in `XPRules`**, which is pure and tested. The service only reads and writes the store. To rebalance the game, edit the constants at the top of `XPRules` and nothing else.
- **Farmable actions share one daily cap** (`dailyUsageCap`), not one cap each — separate caps just move the farming around. It clamps rather than refuses, so an award at the boundary pays what's left. One-time and streak awards are never capped.
- **One-time awards are keyed** in `UserProgress.awardedKeys` (an `XPReason` raw value for setup milestones, `streak-7` for streak rungs), so a milestone can't pay twice — including a user who lapses and climbs back to the same streak.
- **The streak follows logging, not app-opening** (the plan's first principle). A lapse resets the streak and *never* the XP, and the card says "מתחילים רצף" rather than "0 days" — nothing in this system punishes or nags.
- **Celebrations are announced through the store, not a return value.** Level-ups and unlocked achievements are appended to `UserProgress.pendingCelebrations` in the order they happened (a patch, then the level it pushed you to); `HomeView` shows the head as `CelebrationToast` and `ProgressService.dismissCelebration` pops it once the toast has animated out. The XP that triggers one is usually earned inside a sheet that's already dismissing itself, so the celebration has to outlive the screen that caused it — and one earned just before the app was killed still fires on the next launch. The toast waits while any sheet or alert presented from `HomeView` is up (an overlay sits *under* them), and a cancelled run leaves the queue alone so it replays. A pass that unlocks more than `ProgressService.celebrationBatchThreshold` (3) patches queues one "פתחת N הישגים חדשים" toast plus only the level it ended on, instead of a toast each. Tapping an achievement toast opens the profile tab.
- **Sound and haptics** (`Services/CelebrationFeedback.swift`): three moments rising in size — a new transaction (one warm tone, played from `NewTransactionSheet.handleConfirm` for new rows only), an achievement (a two-note steel-drum phrase: `STEEL04` for bronze/silver and the batch toast, `STEEL08` for gold) and a level-up (four plucked-string notes), the last two played by the toast as it slides in. The **budget reminder** is a fourth, separate moment — a nudge, not a reward — so it is deliberately *not* a chime: one solid bell strike (Kenney `bong_001`, `reminder-budget.caf`) with one full, low-sharpness tap. The sounds are **CC0 assets by Kenney**, fetched and prepared by `Scripts/prepare_sounds.py` (credits in `Scripts/SOUNDS_CREDITS.md`) into `OshRat/Sounds/` (each pick names its output file). Two synthesised versions came before them and both were rejected as sharp and cheap — don't go back to generating sounds. Haptics are **crisp transient taps only**, one per note, timed to the onsets the script prints and building to a clearly stronger last tap (Apple's "success" shape); a continuous low-sharpness swell was tried and felt like a cheap buzzer. The audio session is `.ambient`, so the silent switch mutes them and other audio keeps playing; a mute toggle belongs on the planned Settings screen. The simulator plays neither haptics nor reliable audio — judge them on a device.
- **Achievements are evaluated from facts, not the XP ledger** — `ProgressService.evaluateAchievements` runs at the end of every entry point, on dashboard appear (catches month closes) and after a deposit payout. It is retroactive: an existing user unlocks what they've already done, patches *and* XP. Anti-farming keys on `Transaction.createdAt` (entry time, stamped by `init`; `nil` = legacy row, counted in totals but never as a spread day), never on the user-chosen `date`. Budget months are only judged after `achievementsEpoch` and only if no budget line changed since before the month began.
- **`LevelProgressCard`** lives on the **profile tab** (`Views/Profile/ProfileView.swift`): level, a bar to the next level, the streak, and what the last points were for (the plan's "always show *why* XP was earned" guardrail, standing in for an XP ledger that phase 1 doesn't have). It sat on the dashboard until the profile tab existed to hold it.
- **`XPLevelBadge`** is what the dashboard kept: a capsule that fills with `LevelProgress.fraction` and carries "רמה N" **inside** it. It rides the **assets card's top edge** at the visual left, opposite the greeting mascot resting on the other end of the same edge — parked there by an `.overlay(alignment: .topTrailing)` on the card whose `.top` alignment guide is redefined as `$0[.bottom] + Theme.Spacing.md`, so its base **hovers** a fixed 16pt above the card's edge. Doing it with an alignment guide rather than a negative `.offset` means the badge's Dynamic-Type height never has to be guessed at from `HomeView`, and the gap holds at every text size. Display-only: the rat in the bottom bar is the single way into the profile, so the badge isn't also a button. Both it and `LevelProgressCard` read `progressRows.first`, so they can't disagree. Three details that are load-bearing: the base is **opaque** (`Theme.Colors.surface`) so it reads as a solid chip rather than a tinted patch of the page, and its shadow is what lifts it off the page; the charge is a **`Rectangle` clipped to a `Capsule`**, not a second `Capsule`, because a rounded growing edge makes it read as a toggle switch; and the label is `textPrimary`, not the accent, because it sits over the fill on one side and the empty track on the other and has to clear 4.5:1 on both. `ZStack(alignment: .leading)` mirrors under RTL, so the charge grows from the visual right.

## Navigation

- `ContentView` routes by data: no `UserProfile` in SwiftData → `OnboardingFlowView`; otherwise `HomeView`. There's no "did the user onboard?" flag — the data is the source of truth.
- `HomeView` is the app shell. It owns the shared chrome — background, the floating glass `HomeBottomBar`, the FAB (new transaction), and the global sheets (new transaction, budget editor, account editor) — and switches between tab branches on a `@State selectedTab: HomeBottomBar.Tab`.
- `HomeBottomBar.Tab`: `home` (raised center button sitting in the notch), `profile`, `transactions`, `analytics`, `calendar` — **two per flank**, so the notch stays centred between equal groups. Right-to-left on screen that reads rat, תנועות, (home), תובנות, יומן. The calendar icon wears a small bell badge (`ReminderBadge`, at `.topTrailing` — visual top-left under RTL) while a budget reminder is pending. Side icons are `HomeBarButton` (brand accent when selected, secondary otherwise); the center is the raised `HomeCenterButton`. The bar is built on the iOS 26 `glassEffect` with a custom `NotchedBarShape`.
- **`HomeBarButton` is generic over its icon**, not a symbol name, because one of the four isn't a symbol. It applies the tint to the *container*, so an `Image(systemName:)` and a bare `Shape` (which fills with the foreground style) colour identically with nothing to remember per call site. The three symbol tabs go through `BarSymbol` so they can't drift apart typographically.
- **`RatHeadShape`** is the profile tab's icon, drawn by hand next to `NotchedBarShape`: SF Symbols has no rat or mouse **animal** glyph (only `computermouse`, `hare`, `pawprint`, `tortoise`), so the app draws its own. It is a **whole rat in profile — crouching, nose to the visual left, tail sweeping up over its back — not a head**, and that is the point: any front-facing rodent head is two lobes above a face, which is the Mickey silhouette, near enough to be someone else's mark. Tilting the ears into ovals, dropping them to the temples and lengthening the muzzle were each tried and each still read as it; the lobes are the tell, not the face under them. Four further things are settled and shouldn't be re-litigated:
  - **Filled, not stroked.** Two attempts at line art failed at ~21pt: the ear lobes merged into the skull's outline and the inner-ear detail read as a pair of *eyes*.
  - **A custom `Shape`'s coordinate space is mirrored under RTL** — confirmed on device, not assumed: drawn nose-left it rendered facing *right*, off the screen edge. The coordinates are pre-mirrored so it faces into the bar.
  - **Every subpath is wound clockwise**, verified by signed area rather than by eye, because `fill` uses the nonzero rule and a disagreeing subpath cancels the overlap into a hole. Mirroring flips winding, so each path is also traversed in reverse to put it back — which is why the curves read tail-first. `addEllipseClockwise` emits the ear to match (`Path.addEllipse` winds the other way and can't tilt).
  - **The tail stays thick.** A naturalistic thin one aliases into a stray wisp at 25pt.
  Authored in a 100×100 box and scaled uniformly, so it survives Dynamic Type and a larger rendering needs no second set of numbers.
- The dashboard branch is a plain `ScrollView`; each other tab is wrapped in its **own** `NavigationStack` inside `HomeView`, so it gets its own title + toolbar. **Every tab uses `.navigationBarTitleDisplayMode(.large)`** — תנועות, תובנות, יומן התקציב and הפרופיל שלי read the same way; sheets (filters, editors, Recently Deleted) stay `.inline`. A large title brings its own vertical space, so a screen under one keeps its own top padding minimal rather than stacking a second gap on top. **Bottom clearance on a scrolling screen:** pad with one of the two constants on `HomeBottomBar` (as `.padding(.bottom,)` on a `ScrollView`'s content, or `.contentMargins(.bottom, …, for: .scrollContent)` on a `List`). Pick by what sits at the *end* of the screen:
- `floatingButtonClearance` (~163pt) when the last element is **interactive** — the calendar's "הוספת פריט ליום זה" button, the transactions list's rows (tap to expand, swipe to delete). Clears the bar *and* the floating "+".
- `barClearance` (~98pt) when the last element is just a **card** with nothing tappable at its bottom edge. The "+" may hover over that edge; padding it out costs a chunk of dead space at the end of every scroll.
- **The dashboard is the exception**: it's a plain `ScrollView`, *not* inside a `NavigationStack`, so the bar's `safeAreaInset` **does** reach it. It pads only `Theme.Spacing.md`; `barClearance` there counted the bar twice (measured ~166pt of empty page under the budget card).

Both are full clearances measured from the screen edge. `HomeView` does install the bar as a `safeAreaInset`, but **that inset does not reach the scroll views inside the tab branches** (each sits in its own `NavigationStack`, under a `ZStack` whose background ignores the safe area) — screens measured on the assumption that it did ended up with their last row under the bar. Don't subtract it.
- The dashboard's budget card is a **horizontally paged `ScrollView`** (`BudgetCardCarousel`) — one card per period, swiped to move month-to-month or year-to-year. A nested scroll view on the perpendicular axis is the deliberate choice: it separates the axes *natively* (UIKit locks a pan to whichever direction it starts in), which a custom `DragGesture` cannot — an earlier drag-driven version fought the dashboard's vertical scroll. It bleeds full-width and restores the gutter as `contentMargins`, so pages match the width of the cards above. See the paged-`ScrollView` gotcha in Conventions before widening its window.
- **Widget entry point:** `HomeView` handles the `oshrat://new-transaction` URL from the quick-add widget by opening the new-transaction sheet.
- Feature-local sheets (income/expense editors, the schedule section, calendar add) are presented from within their own screens, not from `HomeView`.
- **To add a tab:** add a case to `HomeBottomBar.Tab`, a `HomeBarButton` (with its icon as a trailing closure) in the bar's `HStack`, and a branch in `HomeView`'s `switch` — then register any new screen files in the pbxproj (see Conventions). `-demoTab <case>` picks it up for free, since `HomeView.initialTab` parses `Tab(rawValue:)`. The flanks currently hold two icons each; a sixth tab means re-balancing them, not appending.

## Settings

There is **no Settings screen yet** — preferences are currently hardcoded to sensible defaults. Planned, in priority order:

- **Business-day shift for income (toggle, default on).** Recurring *income* is auto-placed on the next business day, skipping **Shabbat** (Israel works Sun–Fri) **and Israeli rest-day holidays** — a salary on the 1st shows on the next open day when the 1st is a Saturday, Yom Kippur, etc. Holidays come from `IsraeliHolidays` (computed offline from the Hebrew calendar). It returns an `IsraeliHoliday` with an `isRestDay` flag: only **rest-day** holidays (yom tov + Independence Day, which has a Fri/Sat/Mon observance shift) move a salary; working-day holidays (Hanukkah, Purim, Tu BiShvat, Lag BaOmer) are display-only. Implemented now in `BudgetItem.occurrenceDate(..., shiftIncomeToBusinessDay:)` + `BudgetItem.businessDay(onOrAfter:)`, currently forced on. **Task:** add a `shiftIncomeToBusinessDay` preference (store on `UserProfile`, default `true`), build the Settings toggle, and thread it through to `occurrenceDate` from the calendar/dashboard so the user can disable it.
- **Sound & haptics toggle ("צלילים ורטט", default on)** for `CelebrationFeedback`; until it exists the silent switch mutes the chimes.
- Later: preferred-currency change, manual FX refresh, and a (currently DEBUG-only) data reset.

## Conventions

- Group code as: `Models/`, `ViewModels/`, `Views/` (with a subfolder per feature), `Services/`, `DesignSystem/`. Visual constants (colours, spacing, typography, `.cardStyle()`) live in `DesignSystem/Theme.swift` — use them, don't hard-code. Shared controls live there too: `PickerRowLabel` is the bordered "opens a `Menu`" row used by the transaction sheet's account/category pickers and the budget editor's category picker, so a "choose one" control looks the same everywhere. Every **category** menu fills it with `CategoryMenuContent` (income, then expenses grouped צרכים / רצונות / אחר, alphabetical by Hebrew collation, each with its glyph) — the transaction sheet, the budget expense editor and the transactions filter all use it, so never hand-roll a category list.
- **Soft delete vs hard delete (crash trap).** Almost everything in the app soft-deletes — `deletedAt` is stamped, the object stays perfectly valid, and a row may safely hold its `@Model`. `RecentlyDeletedView` is the *only* screen that hard-deletes, and `modelContext.delete` invalidates the object **immediately** while SwiftUI keeps the outgoing row alive to animate it away. A row that reads `transaction.title` (or worse, walks `transaction.category?.name`) during that animation traps with "This model instance was invalidated because its backing data could no longer be found in the store". So on that screen rows render from `DeletedItem` value snapshots and `@State` holds a `PersistentIdentifier`, never a model — `ModelContext.model(for:)` turns it back into an object at the one moment one is needed. Apply the same rule to any future hard delete.
- One type per file *ideally*, but tightly-coupled private helper views/types are co-located with their feature file (matches the existing code).
- Keep views small; push logic into view models / testable value types (e.g. `AnalyticsReport`, `BudgetSchedule`) and services.
- Comment the *why*, not the obvious *what*. When you add a dependency or make a structural choice, say so and explain why.
- **Art assets (`OshRat/Assets.xcassets`).** The catalog sits inside the synchronized `OshRat/` group, so adding or moving art needs **no** pbxproj edit (unlike code — see the next bullet). Mascot and wardrobe art is filed by folder group:
  ```
  Mascots/<Character>/Poses/   400×520 bust crop — spot art for toasts, headers, onboarding
  Mascots/<Character>/Rig/     360×660 full body — the shared wardrobe canvas
  Accessories/{Hats,Outfits,Props,Backgrounds}/   wardrobe items, one folder per slot
  ```
  **The subfolder tells you which canvas to draw on** — that's the whole point of the split, because layers only register when they share a viewBox. `Props` is the plan's front *accessory* slot (glasses, a coin, a bag), named so it doesn't read as `Accessories/Accessories`.
  Asset names are `<character>-<crop>-<pose>`. Two characters so far:
  - **`Classic`** — the suited, hatted rat in today's screens. Grandfathered names: `rat-mascot-*` (bust), `rat-fullbody-*` and the articulated `rat-part-*` (the Analytics rig) on the 360×660 canvas.
  - **`Bare`** — the hatless, suitless body the wardrobe dresses. `bare-bust-{base,wave,present,thumbsup}` and `bare-fullbody-{base,wave,confident,thumbsup,cheer}`.

  A new character or style is a new folder beside them with its own prefix.
  **Within a character the poses differ only in one arm** — for Bare, 33–35 of 37 drawing elements are byte-identical to `bare-fullbody-base`, with the skull, both ears, torso, legs, feet and tail at identical coordinates in all five. So one hat, glasses or background asset registers on *every* pose; a **sleeved** outfit will not, since a sleeve has to track the moving arm. Keep outfits torso-only or cut the sleeve per pose.
  **None of these folders provide a namespace**, deliberately: asset names stay flat, so `Image("rat-mascot-wave")` keeps working no matter which folder the file sits in, and the asset name stays usable as the catalog key. The cost is that **names must be unique across the whole catalog** — prefix per character, `item-<slot>-<name>` for wardrobe items. Moving art between folders is therefore free; verify a move with `xcrun assetutil --info <built>.app/Assets.car` rather than a build alone, which passes either way.
  **Rarity is a field in the code catalog, not a folder.** Rarity is a balancing decision that gets re-tuned; folders are for the slot, which never changes. (Per GAMIFICATION.md the item catalog lives in code, not the database.)
- **Adding files (gotcha):** only the `OshRat/` folder is a synchronized Xcode group. New files under `Models/`, `Views/`, `ViewModels/`, `Services/`, `DesignSystem/` are **not** auto-detected — register each in `OshRat.xcodeproj/project.pbxproj` by hand (a `PBXBuildFile`, a `PBXFileReference`, an entry in the parent group's `children`, and an entry in the target's `PBXSourcesBuildPhase`). A file the **test targets** also need (anything `Account.swift` and friends reference) needs its own `PBXBuildFile` per target — three in total. **Object IDs must be unique across the whole file**: reusing one that already exists doesn't fail the lint, it silently rebinds the entry to the *other* file, and the new source is simply never compiled ("cannot find type X in scope" with no "Compiling X.swift" line). Validate with `plutil -lint OshRat.xcodeproj/project.pbxproj`, then confirm membership really resolved: `plutil -convert json -o /tmp/pb.json … ` and walk each target's sources phase from `fileRef` to `path`.
- **Build check:** `xcodebuild build -scheme OshRat -destination 'platform=iOS Simulator,name=iPhone 17 Pro'`.
- **Paged `ScrollView` gotcha:** every mounted page's body runs on each render, so per-page work multiplies by the page count — `HomeView.report(for:)` rebuilds a `BudgetVsActual` from the entire ledger, and `.defaultScrollAnchor(.center)` measures the whole row, which defeats `LazyHStack` — so the row is a plain `HStack` (a lazy one sized itself from the pages built so far and clipped the tallest card's bottom off). A ±240-period window meant ~481 ledger scans per render and a pinned main thread on a real device. Keep the window small and re-base it around the visible page instead of mounting a wide range.
- **`List` row-growth gotcha:** don't animate a `List` row's *height* to reveal content — insert a **separate row** instead. `List` is a UIKit collection view: a row that grows has its cell frame animated from its centre while SwiftUI has already laid the content out at the final size, so the content is misplaced mid-animation. Recorded frame by frame on the transactions list: the tapped row vanished for three frames and slid back in on opening, and drew over its neighbour on closing — and no SwiftUI-side fix inside the row (a fade instead of a slide, `.clipped()`, top-pinned content) changed that. Row insertion and removal are the collection view's own animations and are smooth. Also avoid a bouncy spring on list motion; an overshoot reads as the list wobbling.
- **Previewing a drawn shape without a build:** `qlmanage -t -s 1400 -o <dir> file.svg` rasterises an SVG, so a candidate `Shape` can be authored as SVG path data and eyeballed in seconds instead of a build/install/screenshot cycle each guess. Lay the candidates out in one sheet **and repeat them at icon size** (`transform="... scale(0.25)"`) — `RatHeadShape` looked fine large while its tail aliased to a wisp at 25pt, which only the small row showed. Note SVG fills each `<path>` separately whereas a SwiftUI `Shape` fills one `Path` of subpaths, so the preview will not reveal a winding conflict; check that by signed area.
- **Verifying UI on the simulator is limited:** `simctl` boot/install/launch/screenshot work, but AppleScript automation is blocked, so gestures can't be driven. A clean build is not evidence that a gesture or scroll change behaves — say so, and test interaction on a device. What *can* be driven is the starting state: `xcrun simctl launch booted com.rotem.OshRat -demoScenario saver -demoTab analytics` fills the store and opens on a given tab (see the demo-data bullet above), so a data-driven screen can be screenshotted without tapping through onboarding first. `-demoEquip <item-id>` and `-demoWardrobe` do the same for the avatar and the wardrobe. Install the app from `BUILT_PRODUCTS_DIR` (`xcodebuild … -showBuildSettings | grep " BUILT_PRODUCTS_DIR"`), not whichever `DerivedData/OshRat-*` folder a `find` hits first — a stale one can hold an old template build that looks exactly like the simulator being stuck (the real app's UI is Hebrew; English means the wrong build). **Animations can be verified** even though they can't be triggered by touch: a temporary `// TMP-…` hook calls the real action on a timer (e.g. `toggleExpand` after 4 s), `xcrun simctl io booted recordVideo --codec=h264 out.mov` records it, and a few lines of Swift with `AVAssetImageGenerator` (zero tolerance, ~30 fps steps) tile the frames into a contact sheet. That is how the list's expansion glitch was seen, diagnosed and confirmed fixed; strip the hook afterwards.

## Current status

Onboarding, the dashboard (assets + budget-vs-actual cards), transactions (list, add, edit, transfers), the Analytics roadmap, and the budget calendar with scheduled items are all implemented. **Budget reminders** nudge the user to log today's scheduled lines (a toast with its own bell sound, plus a badge on the calendar tab), and calendar rows swipe to log (pre-filled sheet) or delete, with logged occurrences drawn grey. The dashboard's budget card **swipes between periods** — month or year, past or future — via `BudgetCardCarousel`. Transaction rows in the list **expand** on tap into an insights card, inserted as a row of its own so the opening is smooth. It leads with a **bar for the category's budget** that month ("₪620 מתוך ₪1,000"), then recurrence/cadence, amount-vs-average, last-seen, day pattern (all computed in the pure `TransactionInsights` value type), the note, any **file attachments** (receipts/invoices added from Camera/Photos/Files, viewed via QuickLook; in the sheet the add button stays pinned beside the strip and newest files show first) and similar past rows, three visible and scrolling to ten. Transactions can also be **multi-selected** (long-press, then tap) and deleted as a batch, **copied** with a swipe into a pre-filled sheet, and **sorted** by date or by amount. Each active filter is a **removable chip** under the search field, dates are one-tap presets (this month, last month, this year, the last 7/30/90 days, or a custom range), and the filters survive a tab switch. **Search is forgiving** — final letters, niqqud, spelling variants, typos weighted by Hebrew keyboard distance, and a keyboard left on English — and the list pages rows in so a long ledger stays smooth. Deleting an account or transaction is a **soft delete** recoverable from `RecentlyDeletedView` (whose rows render from value snapshots — see the hard-delete trap in Conventions), and a home-screen **quick-add widget** deep-links into the new-transaction sheet. Navigation is a custom glass bottom bar (`HomeBottomBar`) with Profile / Transactions / Home / Analytics / Calendar (right to left); `HomeView` switches between them and owns the shared chrome (bottom bar, FAB, sheets). The **profile tab** — reached via the hand-drawn `RatHeadShape` at the bar's right edge — holds the avatar, the onboarding details, the XP card and the achievements shelf, read-only; the avatar (and the dashboard's greeting rat) is the user's own dressed rat and opens the **wardrobe**, where hats unlock by level.
